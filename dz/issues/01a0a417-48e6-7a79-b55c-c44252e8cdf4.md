An error raised through `internal/errors`' `hideStackFrames()` wrapper --
which is essentially every `ERR_*` validation error Node's lib throws, and
every `AssertionError` from `assert.strictEqual`/`deepStrictEqual` -- carries
**no stack frames at all** in a `build-native` artifact built with the
default native built-ins. The same artifact built with `--bytecode-builtins`
names the failing user line, and so does a plain `hermes-node` run.

Measured (macOS arm64, `cmake-build-release`, same kit). One user script,
three builds:

```js
var assert = require('assert');
function boom() { assert.strictEqual(1, 2); }
try { boom(); } catch (e) { console.log(String(e.stack).split('\n').slice(-3)); }
try { require('path').join(1); } catch (e) { console.log(String(e.stack).split('\n').slice(0,3)); }
```

| build | `assert.strictEqual` | `path.join(1)` |
| --- | --- | --- |
| plain `hermes-node` | `at anonymous (t.js:...)` | `at join (path:1339:21)`, `at anonymous (t.js:...)` |
| `build-native --bytecode-builtins` | `at anonymous (t.js:2:37)` | `at join (path:1339:21)`, `at anonymous (t.js:8:27)` |
| `build-native` (native built-ins) | (no frames) | (no frames) |

Only the built-ins' compilation mode differs between rows two and three --
the user's own modules are compiled natively in both.

`assert.ok(false)` and a plain `new Error()` in user code are unaffected, as
is a synchronous `fs.statSync` ENOENT. What the three failing cases share is
`libjs-node/internal/errors.js:541`:

```js
Error.stackTraceLimit && ErrorCaptureStackTrace(error, wrappedFn);
```

The likely mechanism is that Hermes's `Error.captureStackTrace(err, fn)`
cannot match `fn` against a frame belonging to a natively compiled unit, and
discards every frame rather than leaving the stack intact the way V8 does
when `constructorOpt` is not found on the stack. Not confirmed against the
Hermes implementation.

Impact is diagnosability, not correctness: the error, its `code` and its
message are all right, so nothing computes a wrong answer. But an
`ERR_INVALID_ARG_TYPE` out of a native artifact says nothing about where it
came from, which is the case where a stack is worth most.

Found while greening `check-hermes-node-native` (Task 9 of the native
built-ins plan). No test in that corpus fails because of it -- the two tests
whose output differs, `node-tests/parallel/test-fs-{readdir,stat}.js`, fail
for an unrelated path reason in both modes and merely print shorter traces
natively -- so the suite is green with this open.

Related: `01a0a0d5-7fcd` (native frames carry no location in structured
CallSites) is a different symptom of native frames being second-class in
stack capture.
