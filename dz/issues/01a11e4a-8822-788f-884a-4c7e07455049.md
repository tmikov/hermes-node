`examples/hermes-parser-ast-wasm`'s parser -- hermes-parser's 768,303-byte
WebAssembly module -- fails on large inputs when run by Hermes, while Node
parses the same input. Found while measuring native Wasm in build-native
(2026-10-08; recorded in `docs/superpowers/plans/progress-native-wasm.md`).

Measured with inputs made by concatenating `libjs-node/` files:

- 120 files (1,639,255 bytes): `memory.copy: out of bounds memory access`
- all 349 files: `unreachable executed`
- a 316,194-byte input parses fine.

It fails identically in all three ways the module can run here:

- the plain unbundled `hermes-node ast.js <input>` (Wasm compiled to bytecode
  at run time);
- a `build-native --bytecode-wasm` artifact (baked bytecode);
- a default `build-native` artifact (the module compiled natively by shermes).

So it is not in the cache, the container or the native backend: the bytecode
and native paths share only the Wasm frontend and IR generation, which points
there (or at a runtime helper both call, e.g. memory growth or bulk memory).
Wasm is a Hermes feature, so the defect is Hermes's; filed here until it is
reproduced standalone and moved to the Hermes tracker.

Next step: reproduce with the `hermes` binary and the raw module (extract the
bytes as `progress-native-wasm.md` Task 1 describes), and check whether the
failing input crosses a memory-growth boundary.
