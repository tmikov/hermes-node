The empty-value check for `--vm=` was moved from the parse loop into
`checkToolOptions()` (`tools/hermes-node/hermes-node.cpp`), to match the
convention every other empty-value flag follows -- `--dump-bytecode=`,
`--out=`, `--build-exe=`, `--kit=`, `--cc=` -- and so that `--vm=` and
`--vm ""` give the same named error rather than two different ones.

That fixed the inconsistency it was meant to fix, and introduced a small
ordering change nobody has decided is right or wrong. `checkToolOptions()`
tests the verb conflicts before the empty values, so when BOTH mistakes are
present at once the verb message now wins:

    $ hermes-node --vm= --dump-bytecode=/tmp/x.js
    Error: --vm cannot be combined with --dump-bytecode.

    $ hermes-node --vm= /tmp/x.js
    Error: --vm requires a value

Before the move, the inline check fired first and unconditionally, so the
first command reported "requires a value" regardless of argument order.

Both messages are correct in isolation, and both spellings of the empty value
agree with each other in every case tested, so this is a wording choice for a
doubly-invalid command line rather than a defect. No test covers the
combination, which is why nothing caught the change.

Worth either pinning the current order with a test, or deciding the empty
value should be reported first because it is the more specific mistake.
Raised by the scoped re-review of the final fix wave and recorded rather than
resolved.
