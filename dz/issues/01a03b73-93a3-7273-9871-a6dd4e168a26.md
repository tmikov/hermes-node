`--build-exe` needs clang specifically, not merely "a C++ driver", and offers
no way to say otherwise.

The assemble step passes `-Qunused-arguments`
(`lib/build-exe/build_exe.cpp:209`), which is a clang spelling. Measured:

    $ g++ -Qunused-arguments -c t.s -o t.o
    g++: error: unrecognized command-line option '-Qunused-arguments'
    exit 1

So hand-editing `cc:` in the manifest to `g++` fails at the first step, before
the forwarded `driverflag:` list -- also clang-shaped, being whatever CMake
handed clang -- gets a chance to fail too. There is no `--cc` override flag, so
the only way to change the compiler is to edit the generated manifest, and that
does not work.

The accepted design trade is a *linker* on the build machine, which Static
Hermes needs anyway. That is not what this asks for. It asks for one particular
C++ driver, and clang is not installed by default on most Linux distributions.

Two directions, not exclusive:

- Stop needing a compiler for the assemble step at all (filed separately as the
  direct-object-emission task). That removes `-Qunused-arguments` along with the
  step it belongs to.
- Add a `--cc=<path>` override so a user can point at whatever they have, and
  drop or conditionalize the clang-only flags on the driver actually in use.

Related: the manifest's absolute `cc:` path is filed separately -- fixing that
one does not fix this one, since a found-on-PATH `g++` still fails here.

    Design agreed 2026-08-26. Not yet implemented.

    **Measured first.** `g++` and `c++` each assembled the generated `.s` and
    linked the result correctly -- right size, 16-byte aligned base,
    `GNU_STACK RW`. `c++` here is an alternatives symlink to g++-13; on macOS it
    resolves to clang++, which is the platform-appropriate answer. So "requires
    clang" is one flag wide, not an architectural property: the only blocker is
    `-Qunused-arguments`, which g++ rejects outright.

    **Driver resolution.** A `resolveDriver()` in `lib/build-exe/`, returning the
    chosen driver *and how it was chosen*, so `--verbose` can report it and the
    error can name the whole chain:

    1. `--cc=<path or name>` -- explicit, always wins
    2. the manifest's `cc:` path, if it still exists -- keeps "built and used on
       the same machine" byte-identical to today
    3. `fs::path::filename()` of that path, looked up on `PATH` -- same compiler,
       different machine
    4. `c++` on `PATH` -- the portable fallback
    5. otherwise an error naming all four, so the user knows what to pass

    No manifest grammar change: 2 and 3 are both derived from the existing `cc:`
    line. `runCommand` already spawns via `posix_spawnp`, which does the `PATH`
    lookup for 3 and 4 at no cost.

    The order is deliberate rather than "portable first". A kit cut with clang
    using `-stdlib=libc++`, `-flto` (LLVM bitcode in the archives) or an ASAN
    configuration will not link under g++, so the compiler that cut the kit is
    preferred when available and `c++` is the graceful degradation. Failures are
    loud -- an unrecognized flag, or undefined symbols -- never silent.

    **Flag suppression.** Run `<driver> --version` once and add
    `-Qunused-arguments` only when the output contains `clang`. The
    whole-`driverflag`-list forwarding stays exactly as `build_exe.h` argues it
    should; this makes only its noise suppression driver-appropriate. `-w` was
    considered, since both drivers accept it, and rejected: the header requires
    that a real assembler diagnostic about our generated file stay visible, and
    `-w` would hide one.

    `$CXX` is deliberately **not** honoured. A `CXX` exported for an unrelated
    build silently deciding which compiler links your executable is the kind of
    action at a distance this change exists to remove.

    **A note on the header's justification.** `build_exe.h` defends
    `-Qunused-arguments` as "Clang-only, which this project already requires (see
    CLAUDE.md)". That conflates two people: CLAUDE.md requires clang to *build
    hermes-node*, which is our constraint, and says nothing about the app
    developer *consuming* a kit, which is whose machine this runs on. Worth
    rewriting when this lands.

    Implemented 2026-08-26, as designed above, with two corrections the design
    did not anticipate. Both were found by running the thing rather than by
    reading it.

    **Correction 1: --cc replaces the candidate list, it does not head it.** The
    design had --cc as candidate #1 of four. Running `--cc=/nope/nothing`
    against a real kit produced a working 184 MB executable, silently, linked
    with a different compiler. An override that cannot be run is now a hard
    error naming what it tried. Pinned by
    `ResolveDriverDoesNotSubstituteForAnUnusableOverride`.

    **Correction 2: the probe must not require `--version` to exit 0.** The
    first implementation treated a nonzero status as "unusable", which would
    fall back off a working compiler that merely reports its version oddly --
    and it broke two existing tests that use `false` as a stand-in driver.
    `--version`'s exit status answers neither question being asked. Only exec
    failure counts now: `posix_spawnp`'s error on glibc, or exit 127 elsewhere.

    **Also fixed while there:** the --verbose note said "the kit recorded X,
    which was not usable here" even when --cc had skipped X without trying it.
    `recordedDriverWasRejected()` now gates it, and the no-driver error no
    longer tells someone who just passed --cc to pass --cc.

    **Verified end to end, not just in unit tests.** With a real ASAN kit:

    - `--cc=c++` (g++ 13.3 here) assembles and links a container into a
      standalone executable that runs. This is the whole point of the issue.
    - Default resolution still picks the recorded `/usr/bin/clang++`, so a kit
      used on the machine that cut it behaves exactly as before.
    - A kit whose recorded cc: does not exist falls back to `clang++` from
      PATH, and then to `c++` when the basename is absent too, reporting each.
    - A bad `--cc` exits 1 naming the candidate.

    **Tests:** `BuildExeTest` 11 -> 24 cases. `test/build-exe-tool-errors.js`
    gains the two --cc flag-matrix rows (ungated, so they survive a kitless
    checkout). `test/build-exe-errors.js` has three cases rewritten for the new
    behaviour -- the recorded-cc-absent case is no longer fatal and now asserts
    the fallback note, and two `false`-driver cases lost `-Qunused-arguments`
    from their expected command lines, correctly, since `false` is not clang.
    Full `check-hermes-node` green: 298 unit, 185 JS, 1 unsupported
    (`bundle-yargs.js`, which needs examples installed).

    Not addressed here, and still open on 01a03b73-781a: the manifest's
    absolute shared-library paths. Only the cc: half of that issue is closed by
    this work.
