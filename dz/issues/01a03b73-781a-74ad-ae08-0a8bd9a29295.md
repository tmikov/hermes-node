`kit.manifest` records absolute paths belonging to the machine that cut the
kit, so a kit is only usable on that machine, or one laid out identically.

Two separate sources:

1. `cc:` is `CMAKE_CXX_COMPILER`, taken verbatim as `argv[0]` of CMake's link
   line (`utils/make-kit.py:265`), so it is always absolute -- e.g.
   `/usr/bin/clang++`. It is used verbatim for both the assemble and the link
   (`lib/build-exe/build_exe.cpp:208` and `:229`).
2. Every absolute shared library on the link line is copied into `linkarg:`
   verbatim. `make-kit.py:230` classifies an argument as a system library when
   its basename matches `SHARED_LIB_RE` (`\.(so|dylib|tbd)(\.\d+)*$`) and
   appends it unchanged -- no `{kit}` substitution, no reduction to `-l`. The
   script's own comment records that ICU arrives exactly this way on this tree
   ("the ICU paths sit before libdtoa.a"), so the manifest pins the build
   host's ICU paths too.

The second is the one that will surprise people: it is invisible until someone
runs `--build-exe` on a machine whose ICU lives elsewhere, and the failure is a
link error naming a path the user never chose.

The `cc:` half is nearly free to fix. `runCommand` already spawns via
`posix_spawnp`, which searches `PATH` when argv[0] contains no slash, so
recording the basename `clang++` rather than `/usr/bin/clang++` would work
today with no other change. The library half needs a real decision: reduce to
`-l<name>` plus an `-L`, or resolve at consume time.

Filed 2026-08-26 from a read of the source; not reproduced on a second machine,
because this tree has no kit cut at the moment.
