`test/lit.cfg` and `unittests/lit.cfg` set no `maxIndividualTestTime`, so a
test that hangs holds a worker slot forever rather than failing. Under
`check-hermes-node` the run never returns to report anything, including
other tests that already went red.

This has cost real time once already:
`docs/notes/2026-08-24-macos-validation-results.md:646` records a single hung
test costing 33 minutes, and concludes that a per-test timeout would have
turned it into a clear failure in seconds.

Found again while reviewing the UI compositor's Task 6
(`test/ui-windowless.js`): a mutation of the host's condition-variable
predicate hangs that test. The GTest side of the same branch is bounded --
`unittests/UiHostTest.cpp` carries the `TestWatchdog` pattern from
`unittests/CompositorTest.cpp`, which turns the same regression into a
SIGABRT at 30 seconds -- so the exposure now is the lit half only. The gap is
documented in-tree at `unittests/UiHostTest.cpp` and `test/ui-windowless.js`.

**Neither obvious fix is correct, which is why this is filed rather than
done.**

- `lit_config.maxIndividualTestTime` calls `LitConfig.fatal()` when `psutil`
  is not importable, and `.github/workflows/ci.yml` installs only `python3`.
  Setting it unguarded would abort configuration of the entire suite on a
  machine without psutil -- the exact failure shape that landed in Task 6's
  first round, where one missing lit param raised `KeyError` and nothing ran
  at all.
- A `timeout 60` prefix on a RUN line is not portable: base macOS ships no
  `timeout(1)`. This repo already works around that class of divergence
  elsewhere in `test/lit.cfg`.

The route with in-repo precedent is a small wrapper script invoked from the
RUN line, in the style of `test/fixtures/tty/run-on-pty.py`, which would be
portable and needs no psutil. Applying it suite-wide, rather than to one
test, is the part that deserves its own decision.
