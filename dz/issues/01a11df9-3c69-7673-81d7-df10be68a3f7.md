`cmake-build-asan/hermes/unittests/VMRuntime/HermesVMRuntimeTests` fails five
`StaticHUnitTest` cases when built inside the hermes-node tree:

- `StaticHUnitTest.StartsEmpty`
- `StaticHUnitTest.GrowsAndNullInitializes`
- `StaticHUnitTest.CapacityIsPerRuntimeAndHighIndexFirstWorks`
- `StaticHUnitTest.MallocSizeCountsTheBackingStore`
- `StaticHUnitTest.InitInASecondRuntimeGrowsThatRuntimesArray`

All five assume a freshly created runtime has no SH units (`rt->units ==
nullptr`, `units_size == 0`). This tree's top-level `CMakeLists.txt` forces
`HERMESVM_INTERNAL_JAVASCRIPT_NATIVE` ON before `add_subdirectory(hermes)`,
so Hermes's own InternalJavaScript is a native unit and a fresh runtime has
already registered it: the tests find 8 slots with slot 1 occupied. The run
also ends with an ASAN leak report (43,728 bytes, allocated from
`sh_export_internal_unit` via `Runtime::runInternalJavaScript`).

Pre-existing; seen throughout the native-wasm work (2026-10-08) and not
caused by it. The other 364 tests in the binary pass.

Fix direction: the tests should measure against the runtime's starting state
(capture `units_size` and the occupied slots after creation) rather than
assume zero, or skip when `HERMESVM_INTERNAL_JAVASCRIPT_NATIVE` is on. The
leak is a separate question: whether the internal unit's data is meant to be
freed at runtime destruction.
