A produced executable requires glibc 2.38, which rules out Debian 12 (2.36),
RHEL 9 (2.34) and Ubuntu 22.04 (2.35). Nothing about the program needs
anything that new. Part of 01a03b73-c62a, split out because the fix is a
release-CI change and shares nothing with the ICU half.

**No linker flag can fix this.** Symbol versions are bound against the host's
`libc.so` at link time, so it is decided by the machine that links, not by
how much is linked statically. Measured: an executable built with static ICU
and `-static-libstdc++ -static-libgcc`, whose only remaining shared
dependencies are glibc itself, still requires GLIBC_2.38.

**The floor is accidental.** Everything above 2.34 comes from five symbols:

```
(GLIBC_2.36) arc4random, arc4random_buf
(GLIBC_2.38) __isoc23_strtoul, __isoc23_strtoull, fmod
```

`__isoc23_strtoul` is glibc's C23 redirect of a plain `strtoul` call -- a
header decision, not an API we asked for. The 2.38 `fmod` is a
more-accurate variant of the same function; linking against an older glibc
binds the older one, and nothing here depends on the difference. Only
`arc4random` is a deliberate API choice, and it is the cheaper of the two to
avoid. Everything else the binary imports sits at 2.34 or below -- the 2.34
cluster is just `__libc_start_main`, `dlopen` and the `pthread_*` family,
which all moved into libc at 2.34 and resolve to lower versions when linked
on an older system.

So building against a glibc 2.34 baseline would plausibly cover RHEL 9,
Debian 12 and Ubuntu 22.04 with no source change beyond `arc4random`.

**The fix is a build-baseline change**: link release artifacts in a
manylinux-style container, or on the oldest distribution we intend to
support. That is `.github/workflows/release.yml` plus a container image, not
C++.

**Full `-static` is not an alternative, and is ruled out on its own merits.**
`hermes-node` `dlopen`s `.node` addons. Measured twice: the linker warns that
`dlopen` in a static binary "requires at runtime the shared libraries from
the glibc version used for linking", which reintroduces the dependency the
static link was meant to remove; and the addon is itself a shared object
needing `libc.so.6` and `ld-linux` (checked against
`cmake-build-asan/hello_addon.node`). A runtime that loads native addons
needs a dynamic glibc present. Static glibc is also LGPL-encumbered in a way
static libstdc++ is not, which is worth a real check if it is ever
reconsidered.
