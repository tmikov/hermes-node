`tools/hermes-node-ui/ui_module_nowindow.cpp` is the stub that makes
`require('hermes-node:ui')` succeed on a build with no GPU backend, so a
script gets a rejected promise explaining there is no window support instead
of `MODULE_NOT_FOUND`, which is indistinguishable from a typo.

Its *gate* is verified: `test/ui-no-window-support.js` was confirmed to
execute rather than skip by forcing `ui-gpu` off. Its *text and delivery* are
not. On Linux the stub never runs, because `ui-gpu` is on; on macOS it would
run, but nothing there asserts it. The stub is currently checked by compiling
it (`clang++ -std=c++17 -c -Wall -Wextra` clean, emitting `initUiModule`).

That is the best cheap verification available on a Linux machine, and the
failure direction is right -- a drifted sentence reds macOS CI loudly rather
than passing quietly. But it leaves one assertion in the suite resting on a
compile rather than on behaviour.

The stub has **no platform-dependent code at all** -- pure NAPI plus a
string -- so it can be exercised platform-independently: a GTest that builds
a `napi_env`, calls `initUiModule`, invokes `createWindow` and drains the
rejection would pin both the text and the promise delivery on Linux, and
remove the unverified assertion entirely. The cost is a unit test with a
runtime harness, which is why it was not done inline.

Worth doing when something else needs a NAPI-level test harness in this
area; not worth standing one up alone.
