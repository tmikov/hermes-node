A DNS query whose server never answers never calls back, and the process
waits forever, when the per-try timeout is above one second -- which includes
the c-ares default.

Found 2026-11-19: the macOS run of the suite hung in `test-dns-resolve.js`
under parallel load.

Cause, in `lib/bindings/node_cares_wrap.cpp`: `ChannelWrap::startTimer()`
armed the c-ares timeout timer one-shot, with a delay from `ares_timeout()`
capped at 1000 ms, and `timerCb` did not re-arm it. `startTimer()` ran only
from the socket-state and poll callbacks, so with no reply the timer fired
once, before c-ares's deadline, expired nothing, and was never armed again;
no socket event ever arrived to ask c-ares to expire the query. A per-try
timeout under the cap (e.g. `{timeout: 500, tries: 2}`) happened to survive.

Measured against an unreachable server with default options: Node calls back
with `ETIMEOUT` after about 24 s; hermes-node never did.

Node (`src/cares_wrap.cc`) uses a repeating timer: `StartTimer()` starts it
when the first socket appears, with the channel's timeout clamped to
(0, 1000] ms as both delay and repeat, `ares_poll_cb` calls
`uv_timer_again()`, and `ares_sockstate_cb` calls `CloseTimer()` when the
last socket closes.
