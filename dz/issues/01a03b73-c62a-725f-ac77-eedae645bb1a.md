A `--build-exe` artifact runs on the machine that built it, and on
distributions whose glibc is at least as new. That is short of the
hand-someone-a-file-that-runs promise a single-file executable makes.

**The ICU half of this issue is gone** -- 01a03c05-01a4, fixed 2026-09-02.
Hermes now implements normalization, case conversion, collation and date
formatting from generated tables, and nothing links ICU any more. What
remains is glibc and the C++ runtime.

Measured on a `--build-exe` artifact from the current tree (counts are
`ldd` lines, including the vdso and the loader, so they compare directly
with the nine-line figure this issue recorded when ICU was still linked):

    $ ldd app
        linux-vdso, libm.so.6, libstdc++.so.6, libresolv.so.2,
        libgcc_s.so.1, libc.so.6, ld-linux-x86-64.so.2      -> 7

    $ objdump -T app | grep -o 'GLIBC_[0-9.]*'    -> up to GLIBC_2.38
    $ objdump -T app | grep -o 'GLIBCXX_[0-9.]*'  -> up to GLIBCXX_3.4.31

So the floors are glibc **2.38** and GLIBCXX **3.4.31**; the ICU 74 pin is
simply absent. Against them: Debian 12 has glibc 2.36, RHEL 9 has 2.34,
Ubuntu 22.04 has 2.35. Each fails to start, with a dynamic-linker error
rather than anything this project controls.

**The C++ runtime half is now a two-flag fix, and it was not before.** This
issue previously recorded, correctly at the time, that `-static-libstdc++
-static-libgcc` bought nothing visible: `libicuuc` and `libicui18n` are
themselves C++ and pulled `libstdc++.so.6` back in, which made it
static-ICU-or-nothing. With ICU gone, that coupling is gone with it.
Measured by adding the two flags to a copy of `kit.manifest` and relinking
the same container:

| build | ldd lines | GLIBCXX floor | size |
|---|---|---|---|
| baseline | 7 | 3.4.31 | 188.5 MB |
| `+ -static-libstdc++ -static-libgcc` | 5, all glibc | none | 190.6 MB |

The second artifact runs correctly and imports no `GLIBCXX_*` symbol at all;
its only shared libraries are `libm`, `libresolv`, `libc` and the loader.
Sizes are an ASAN Debug build and mean nothing in absolute terms; the
+2.1 MB delta is the real number, and it matches the +2.1 MB measured for
the same two flags back when they were useless.

Not split into its own issue, because it is two flags and one decision
rather than work. **That decision was taken on 2026-09-03: adopt them for
release artifacts, but only after the baseline below is settled**, and
re-measure there rather than carrying today's numbers over.

One caveat found on 2026-09-03: `-static-libgcc` *adds* two glibc imports of
its own, `_dl_find_object@2.35` and `arc4random@2.36`, pulled from the
host's libgcc. Both sit under the 2.38 ceiling, so they cost nothing today
-- but they would become the binding constraint if the baseline ever went
below 2.35. Settle the baseline first, then re-measure these two flags
there.

**What is actually left is the glibc floor.** No linker flag can lower it --
symbol versions bind against the host `libc.so` at link time. 01a03c05-2967
has the detail: five symbols account for everything above 2.34, and the fix
is a release-CI build baseline, not C++.

**The 2026-08-26 scope decision was revisited on 2026-09-03.** It read "out
of scope for now" because a portable Linux binary needed an ICU answer *and*
a glibc answer, and neither was small. The ICU answer arrived from upstream.
The glibc half turns out to need no code at all: every symbol above 2.34 is
a feature detection or a header redirect that resolves the other way when
built against an older glibc, so the whole floor moves with the build
container and nothing in this repo has to change. 01a03c05-2967 carries the
six-row table and the mechanism behind each one.

So the remaining distance is one CI change plus a choice of baseline, rather
than two open problems.

**The baseline was deliberately deferred on 2026-09-03.** It is a
support-matrix call, not a measurement, and it was left open with the
technical groundwork done rather than decided under time pressure.

For whoever picks it up, that groundwork is now more than groundwork: the
glibc 2.28 option has been built and run end to end, and 01a03c05-2967 has
the numbers. hermes-node compiles unchanged in `almalinux:8`, the binary
requires nothing newer than `GLIBC_2.28`, and it runs on Debian 11, Rocky
Linux 9 and Ubuntu 24.04 -- where the current host-built binary dies at the
dynamic linker. 2.28 is also Node's own Tier 1 x64 requirement
(`BUILDING.md`: Ubuntu 20.04, Debian 10, RHEL 8), which is the argument for
picking that number over another.

The toolchain cost is lower than this issue first assumed. Stock AlmaLinux 8
appstream carries clang 21.1.8 and cmake 3.26.5, so nothing exotic is
needed; only `ninja-build` is absent, and Makefiles serve. Ubuntu 20.04 is
the option that is actually ruled out, on cmake 3.16 against our 3.21
minimum.

What remains genuinely undecided is the support matrix itself, and whether
the CI change is worth making now. This issue stays open on that alone.

macOS is unaffected -- a produced macOS binary needs only OS-provided
libraries.

**Still ruled out:** full `-static`, because the runtime `dlopen`s native
addons (see 01a03c05-2967 for the two measurements); and musl/Alpine, which
would be a separate build target if we want it at all.

Note this is a property of how `hermes-node` itself is built, so it is
inherited by every produced executable; nothing in the `--build-exe` code
path causes it.

    Rescoped 2026-08-26 after measuring every option on real artifacts. This is
    now the umbrella; the two halves that have owners are split out.

    **Decision: a platform-independent Linux binary is out of scope for now.** It
    needs an ICU answer AND a glibc-baseline answer, and neither is small. A
    produced executable runs wherever glibc >= 2.38 and `libicu*.so.74` are
    present -- Ubuntu 24.04 and its relatives, on any number of machines --
    and nowhere else. The ICU soname is an exact match rather than a
    minimum, so newer distributions are excluded as well as older ones. That
    is a documented limitation rather than a bug someone is working on.
    macOS is unaffected -- a macOS binary needs only OS-provided libraries.

    Split out:

    - **01a03c05-01a4** (`hermes`): the ICU dependency, which is fifteen
      functions serving four JS features. Fix lands in the Hermes submodule.
      Preferred direction, deliberately not scheduled.
    - **01a03c05-2967** (`build-exe`): the glibc symbol floor, which no linker
      flag can lower. Fix is a release-CI build baseline.

    **Measured, so nobody has to redo it.** Three executables built from one
    container by editing a kit manifest, all of which run correctly:

    | build | shared deps | size |
    |---|---|---|
    | baseline (clang, shared) | 9 | 186.1 MB |
    | `+ -static-libstdc++ -static-libgcc` | 9 | 188.2 MB |
    | `+ static ICU` | 4 (all glibc) | 224.3 MB |

    Sizes are an ASAN Debug build and are not representative in absolute terms;
    the +36 MB that static ICU adds is roughly constant, though, since 29.4 MB
    of it is `libicudata.a`. On a Release binary of ~40 MB that is close to a
    doubling.

    **libstdc++ and ICU are coupled, which was not obvious.**
    `-static-libstdc++` removed every `GLIBCXX_*` symbol requirement from the
    binary and yet `libstdc++.so.6` stayed in `ldd` -- because `libicuuc.so.74`
    and `libicui18n.so.74` are C++ and pull it in themselves. So the "cheap free
    fix" this issue originally described buys nothing visible on its own. It is
    static-ICU-or-nothing.

    **The stopgap that exists today**, if portability ever becomes urgent before
    either child is done: static ICU plus static libstdc++/libgcc, via
    `HERMES_USE_STATIC_ICU=ON` and `make-kit.py` emitting `.a` paths. Behaviour
    is identical, the ICU 74 pin disappears, and the cost is the +36 MB above.
    Deliberately not filed as its own issue -- it is an option, not work anyone
    intends to do.

    **Not fixable by any of this:** the glibc floor (see 01a03c05-2967), and
    full `-static`, which is ruled out because the runtime `dlopen`s native
    addons.

    Related: 01a03b73-781a's remaining half is the manifest's absolute ICU `.so`
    paths, which largely evaporates if the ICU dependency does.
