`--vm=-Xjit=on`, `--vm=-Xjit=force` and a bare `--vm=-Xjit` are accepted by
hermes-node, run the program and exit 0, with no JIT compilation and no
message. The `hermes` binary, built from the same submodule, refuses:

    $ hermes -Xjit=on script.js
    JIT is not enabled in this build
    exit=1

Its guard is `hermes/tools/hermes/hermes.cpp:75-80`:

    #if !HERMESVM_JIT
      if (flags.DumpJITCode || flags.JIT != JITMode::Off) {
        llvh::errs() << "JIT is not enabled in this build\n";
        return EXIT_FAILURE;
      }
    #endif

So hermes-node diverges from the binary whose flag spellings and semantics it
exists to mirror, and it diverges in the direction this feature refuses
thirteen other flags to avoid: a flag that parses, sets a real RuntimeConfig
field, and does nothing observable. `--vm-help` lists it and promises "JIT
mode (default off)".

Why it does nothing: `HERMESVM_ALLOW_JIT` is 0 in this build -- Hermes's own
default, which this project never overrides, in CMakeLists.txt or in CI -- so
`JITContext` compiles to a stub whose constructor discards its argument,
`JITContext(bool enable) {}`, with `isEnabled()` and `shouldCompile()`
returning false unconditionally (`hermes/include/hermes/VM/JIT/JIT.h`).

## Measured, and narrower than it first looks

Only the mode flag diverges. The other three already mirror hermes; do not
"fix" them.

| flag | hermes | hermes-node |
| --- | --- | --- |
| `-Xjit=on` / `=force` / bare | refuses, exit 1 | accepts silently -- **the bug** |
| `-Xjit=off` | runs, exit 0 | same |
| `-Xjit-threshold=5` | runs, exit 0, inert | same |
| `-Xjit-memory-limit=1m` | `'1m' value invalid for uint argument!` | same |

Hermes's check tests only the mode, so a threshold with the JIT off is inert
there too, and `-Xjit-memory-limit` is a plain `uint32_t` rather than a memory
size, so both parsers reject the suffix identically.

## Complication for whoever takes this

`HERMESVM_JIT` -- the macro `JIT.h` and `hermes.cpp` gate on -- is never
defined anywhere in this checkout: not in any `CMakeLists.txt`, `.cmake` or
`.in` file, and it appears zero times in the configured `build.ninja`. It is
only ever read in `#if`, where an undefined macro is 0. Setting
`HERMESVM_ALLOW_JIT=1` adds JIT sources to the build but still does not define
it. So on this branch the JIT is off unconditionally, and a build-conditional
check would be conditional on something that never changes.

Two options, and choosing between them is the substance of this issue:

1. **Mirror hermes literally** -- the same `#if !HERMESVM_JIT` guard, the same
   message, exit 1. Correct today, and automatically correct if that macro
   ever starts being defined. May need the define propagated to
   `lib/vm-options/` the way `HERMES_CHECK_NATIVE_STACK` and
   `HERMES_MEMORY_INSTRUMENTATION` already are (see
   `lib/vm-options/CMakeLists.txt`).
2. **Refuse unconditionally** with hermes's wording. Simpler, equally accurate
   today, silently wrong the day the JIT is enabled.

Option 1 is the one that means "mirror hermes's behaviour".

Found while reviewing the VM options feature; deliberately recorded rather
than changed, so the behaviour is written down instead of rediscovered.
