Two configurations the Metal backend (Task 16) has guards for and that
were never run.

**Display sleep.** Sokol marks its swapchain invalid while its obscured
timer runs, which starts on an occlusion change; the backend then submits
nothing and sends no frame tick (`present: swapchain invalid; nothing
submitted`). The only cause a test produces is miniaturizing
(`test/ui-metal-occlusion.js`). A display going to sleep while a window
is open was not tried in Task 16d or 16e: nobody had agreed to
`pmset displaysleepnow` at the machine. Unknown, therefore: whether the
occlusion change arrives before the first frame that gets a nil drawable,
and what the one-second `nextDrawable` timeout looks like to a program.
What was measured nearby: with the swapchain-invalid check and our nil
guard both removed, a miniaturized window's frames did not crash, because
Sokol's Metal `begin_pass` skips a nil drawable itself; and with the
session locked and the display asleep from the start, a `sokol_app`
program gets no frame at all.

**A Release build with asserts off.** Every Mac run was an ASAN Debug
build. Two guards exist specifically because a Sokol assert is compiled
out in Release: `acquireFrameSwapchain` checks for a nil drawable
(`_sapp_mtl_swapchain_next` only asserts it), and
`createGenerationSurfaces` refuses when fewer than 256 id-pool slots are
free (Sokol asserts on an empty pool). Both were read, not run, in the
configuration they are for. CI's macOS `release` job does not set
`HERMES_NODE_ENABLE_UI`, so it does not build this code.

To close this: on a Mac, a Release build with `HERMES_NODE_ENABLE_UI=ON`
and one pass of `check-hermes-node`; and one run of a window program
across `pmset displaysleepnow` with `HERMES_NODE_DEBUG_NATIVE=UI`,
recording the trace.
