The kit shipped in v0.0.2-rc2 cannot be linked on most modern Linux
distributions. `--build-exe` from that release fails:

```
/usr/bin/ld: .../kit/hermes-node-bundle-main.o: relocation R_X86_64_32S
  against symbol `hermesNodeBundleStart' can not be used when making a PIE
  object; recompile with -fPIE
```

**Cause: the build image and the user's machine disagree about PIE.**
AlmaLinux 8's clang defaults to **non-PIE**, so the kit's objects carry
absolute relocations. Ubuntu's clang defaults to **PIE**, and a PIE link
rejects them. Verified both defaults with `clang++ -### -x c++ /dev/null`
in each environment. So the affected set is roughly every PIE-default
distribution -- Ubuntu 22.04 and 24.04, Debian 12, Fedora -- which is to
say most of the audience for a prebuilt binary.

This was introduced by moving the release build into a container
(01a03c05-2967). Before that the kit was cut on ubuntu-latest, whose PIC
objects link happily into either a PIE or a non-PIE executable; the
direction we moved is the one that breaks.

**The CI smoke test cannot catch it, structurally.** The release job builds
an executable with the staged kit and runs it, which is what makes shipping
a kit defensible -- but it does that *inside the same container that cut the
kit*, where the toolchain agrees with itself by construction. Any
kit-versus-host toolchain mismatch is invisible to it. That is the real
lesson here and it generalises beyond PIE.

**Fix, preferred:** configure the release build with
`-DCMAKE_POSITION_INDEPENDENT_CODE=ON`. PIC objects link under both PIE and
non-PIE defaults, so the kit stops caring what the user's toolchain prefers.
Cost is the usual small PIC overhead on x86-64, which distributions accept
as standard.

**Fix, cheap and wrong:** append `linkarg: -no-pie` to the manifest.
Measured to work -- the link succeeds and the executable runs -- but every
produced executable then loses ASLR, which is a poor trade to make on a
user's behalf and silently.

**Also needed, whatever the fix:** the smoke test should link in a
*different* image from the one that cut the kit. A kit's whole purpose is to
be used on a machine that is not the build machine, and nothing currently
tests that. An ubuntu:24.04 container running `--build-exe` against the
staged kit would have caught this before the tag was pushed.

Note v0.0.2-rc2 is published, as a prerelease, with the broken kit in it.

    Fixed. The Linux release build now configures
    `-DCMAKE_POSITION_INDEPENDENT_CODE=ON`, so the kit's objects are PIC and
    link under a PIE-default toolchain as well as a non-PIE one.

    Verified on the configuration that actually failed, not on the build image.
    Rebuilt in `almalinux:8` with PIC, staged a release-shaped tree (binary plus
    `kit/`), and ran `--build-exe` from this Ubuntu 24.04 host with **no `--kit`
    flag**:

    - The relocations that caused the failure are gone. `hermes-node-bundle-main.o`
      referenced `hermesNodeBundleStart`/`End` through `R_X86_64_32S`, absolute;
      it now uses `R_X86_64_REX_GOTPCRELX`, GOT-relative.
    - The link succeeds where it previously died, the executable runs, and
      `readelf -h` reports `Type: DYN (Position-Independent Executable file)` --
      so a real PIE link happened rather than the driver quietly falling back.
    - The glibc floor is unaffected: `hermes-node` still requires nothing above
      `GLIBC_2.28`.

    **The missing guard is added too**, because a fix verified only by hand
    leaves CI exactly as blind as it was. A new `verify-kit-linux` job runs on a
    bare `ubuntu-latest` -- PIE-default, the configuration that broke --
    downloads the tarball a user would download, and builds an executable from
    it with no `--kit`. It asserts `ET_DYN` as well, so a pass cannot be vacuous
    on a host that happened to link non-PIE. `publish` now depends on that job,
    so a kit that cannot link off the build machine can no longer reach a
    release.

    That structural point is the durable one and is worth keeping in mind for
    anything similar: `build-linux`'s own smoke test links inside the image that
    cut the kit, where the toolchain agrees with itself by construction, and can
    therefore never catch a kit-versus-host mismatch. Only a second machine can.

    One nuance worth recording, since it looks like a regression and is not. The
    executable produced *on this host* requires GLIBC_2.38, not 2.28. That is
    correct: the kit supplies objects and the final link binds symbol versions
    against the linking machine's libc. The 2.28 floor is a property of the
    shipped `hermes-node` binary and of executables linked on a 2.28 machine;
    someone linking on Ubuntu 24.04 gets Ubuntu 24.04's floor in their own
    output.

    The defective artifact, v0.0.2-rc2, was deleted along with its tag.
