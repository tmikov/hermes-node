If `createWindow` is rejected late -- in `onSharedContextReady`, after
Sokol's window already exists (the surface allocation, the window object
or the frame origin failing) -- the platform thread keeps running Sokol's
loop and keeps converting every real event into `gInput`
(tools/hermes-node-ui/ui_module.cpp, `uiHandlePlatformEvent`). Nothing
drains it: event delivery opens only from the success path
(`openEventDelivery`), and since the Slice C fix wave there is no published
window either. So the queue grows for as long as the process lives --
every mouse move over a window the program can no longer use.

Narrow: the failure paths are the rare, mostly unrecoverable ones, and a
program that got the rejection usually exits. The fix belongs with Task
15's teardown, which owns what an abandoned window does (stop converting,
or tear the window down). Found by the Slice C whole-slice review.
