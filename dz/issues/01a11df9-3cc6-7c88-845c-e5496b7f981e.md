`cmake --build cmake-build-asan --target check-hermes` does not work when
Hermes is built as a subdirectory of hermes-node. Three independent problems,
found during the native-wasm work (2026-10-08):

1. **Wrong wabt paths.** `hermes/CMakeLists.txt:911-912` pass
   `wat2wasm=${CMAKE_BINARY_DIR}/external/wabt/wabt/wat2wasm` (and the same
   for `wast2json`). `CMAKE_BINARY_DIR` is the *outer* build directory, so
   lit is told `cmake-build-asan/external/wabt/wabt/wat2wasm`; the real tools
   are under `cmake-build-asan/hermes/external/wabt/wabt/`. Nearly every
   `test/wasm` test then fails (measured: 19 pass, 10 xfail, 279 unexpected
   failures under `LIT_FILTER='wasm/'`). `PROJECT_BINARY_DIR` /
   `PROJECT_SOURCE_DIR` would be the Hermes ones.
2. **No Wasm spec testsuite.** `wasm_testsuite=${CMAKE_SOURCE_DIR}/external/wasm-testsuite/tests`
   (line 913) names a directory that does not exist here, so the 62
   `wasm/spec/*` tests fail.
3. **Stale `SHERMES_CC_INCLUDE_PATH`.** The cache holds
   `cmake-build-asan/lib/config:<src>/hermes/include`, but `libhermesvm-config.h`
   is in `cmake-build-asan/hermes/lib/config`. Every shermes test that
   compiles C fails with `libhermesvm-config.h not found`. The default in
   `hermes/tools/shermes/CMakeLists.txt:27-29` uses `PROJECT_BINARY_DIR`,
   which today resolves to the Hermes directory, so this looks like a cache
   entry left from an earlier configuration (the `set(... CACHE ...)` is not
   `FORCE`d); not verified by reconfiguring.

Two more `check-hermes` failures remain with all three worked around, and
look unrelated to the paths: `wasm/cli-run-start.wat` and
`wasm/compile-mixed-imports.wat` (a handle-sanitizer warning on stderr).
