An unhandled promise rejection ends the process through
`triggerUncaughtExceptionCallback` in `lib/bindings/node_errors.cpp` (the
`triggerUncaughtException(err, fromPromise)` binding that
`libjs-node/internal/process/promises.js` calls). That function reports the
error, `fflush`es and calls `_exit(1)`, with no `uv_tty_reset_mode()`. Every
other `_exit()` site restores the terminal first: `processExit`
(`lib/process/node_process.cpp`), `triggerUncaughtException` in the same file,
and `uiBeforeRuntimeCleanup` (`tools/hermes-node-ui/ui_module.cpp`). The
CLAUDE.md "Bootstrap Sequence" section states that every `_exit()` path
restores the terminal; this one does not. `_exit()` runs no `atexit`
handler, and libuv's own restore in `uv__tty_close` is never reached.

Reproduction (`rej.js`), run on a pty with `test/fixtures/tty/run-on-pty.py`:

    process.stdin.setRawMode(true);
    process.on('exit', (c) => process.stderr.write('EXIT-LISTENER ' + c + '\n'));
    Promise.reject(new Error('rejected'));

Measured 2026-11-19:

- hermes-node (cmake-build-asan): prints the `UnhandledPromiseRejection`
  report, `exit status: 1`, `before: ECHO=on ICANON=on`,
  `after:  ECHO=off ICANON=off`, `RESULT: LEFT-IN-RAW-MODE`. No
  `EXIT-LISTENER` line.
- node v24.13.1: `EXIT-LISTENER 1`, `exit status: 1`, `RESULT: RESTORED`.
- Control, hermes-node: the same program throwing from a `setTimeout`
  callback instead (the `triggerUncaughtException` path) prints
  `RESULT: RESTORED`.

The fix is probably the same two lines the other sites have
(`uv_tty_reset_mode()` after the flush), plus a `rejection` case in
`test/test-tty-restore.js`. The same path also runs no `'exit'` listener
(above) and does not pump the loop the way `flushPendingWrites` does for the
other two; that half belongs with 01a1d5c0-d385, which is about how this path
is reached, and a fix to it may move or remove this `_exit(1)` altogether.
