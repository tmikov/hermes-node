`sh_unit_additional_memory_size()` (hermes/lib/VM/StaticHUnit.cpp:206,
Hermes submodule) returns:

    sizeof(unit->runtime_ext) + unit->runtime_ext->templateMap.getMemorySize()
        + unit->runtime_ext->addCacheEntries.capacity_in_bytes();

`sizeof(unit->runtime_ext)` is the size of the POINTER (8 bytes), not the
`SHUnitExt` allocation it points to (`new SHUnitExt{}` in
`_sh_unit_init`), and the generated `UnitData` allocation (the per-unit
symbols/property-cache backing arrays a real shermes-compiled unit emits)
is not counted at all. Task 1 of the native-compilation plan
(docs/superpowers/plans/2026-09-13-native-compilation.md) added only the
new growable units-pointer-array itself to Runtime::mallocSize(); it did
not touch this pre-existing undercount, which predates the plan.

At eight units (the pre-plan cap) nobody noticed. At the scale this plan
targets -- Task 16 measured a real program at 1,541 compiled units -- the
GC heap-size accounting is simply wrong by a growing amount: 1,541 missed
`SHUnitExt` bodies plus 1,541 missed `UnitData` allocations, whatever
those actually total.

Fixing it properly needs an emitted allocation-size field on the unit (a
Hermes codegen change to shermes's code generator, not a native-compat
change), so that `sh_unit_additional_memory_size` has a real number to
add for the `UnitData` piece; the `SHUnitExt` piece is a one-line
`sizeof(*unit->runtime_ext)` fix that could land independently.

Filed from Task 16 of the native-compilation plan; see
docs/superpowers/plans/progress-native-compilation.md for the Step 2b
unit-count measurement this was found alongside.
