`test/ui-present.js`'s third run exercises the stage-2 GL completion probe by
setting no `HERMES_NODE_UI_GL_COMPLETION` override. That makes
`kProbeHandshakeTimeoutMs` (2000 ms, `lib/compositor-gpu/gl_backend.cpp`)
load-bearing for the first time: the other two runs take the early return and
never depended on a frame callback arriving at all.

Two consequences, neither serious enough to block the work that found them.

**A new flake surface.** 2 s is not enormous for a frame callback under
16-way parallel `xvfb-run` in an ASAN build. This suite already carries one
load-dependent failure (see the throughput-floor issue), so a second timing
budget is worth watching rather than assuming.

**A misleading diagnostic.** If `glFenceSync` returns null, `decided` stays
false and the probe falls into the same branch, printing that no frame
callback ran within 2000 ms -- when in fact callbacks ran fine and fence
creation failed. Pre-existing, but only now reachable, because nothing
previously ran the probe under test.

The assertion itself is sound and deliberately excludes this branch from the
accepted set: including it would let a stalled handshake pass. A driver that
legitimately times out waiting on the fence reaches a different, accepted
branch governed by a separate 200 ms budget, so strictness here was not
bought at the cost of portability.

Worth doing if it bites: distinguish "fence creation failed" from "no frame
callback answered" in the message, and reconsider the 2 s budget against
observed CI timings rather than against intuition.
