On 2026-11-25, on the Mac (Apple M4 Max, macOS 27.2, ASAN UI build), one full `check-hermes-node` run failed `test/ui-resize-generation.js`: it ended at its 300 s wrapper limit (status 124). The test alone then passed 6 of 6 in 2 s each, and a second full run was clean. It had passed in every earlier full run there.

What the failed run shows. Output ended `ZERO WRONG {"generation":3,"width":640,"height":480}`. The trace has generation 3 started at 640x480 replacing generation 2 at 320x240, and its last line is `present: swapchain invalid; nothing submitted`. Generation 3 at the window's real size is what the test's header says happens if a real platform event arrives once the window is up, which the test assumes does not. The test then waits for a capture of generation 2; with the swapchain invalid no frame presents, so its frame budget is never used up and it waits until killed.

Not known: which event started generation 3, and what made the swapchain invalid. The window tests run one at a time on macOS (the display lock), so another test's window is not an obvious cause. Someone was using the Mac during that run, and a test window opens centred on their screen without taking focus; a window of theirs covering it, or a click on it, would produce both symptoms. That is an inference, not measured. The same `swapchain invalid` line ended a deliberately broken run of `test/ui-terminate.js` minutes earlier, with no other test running.

Two separate things to settle: whether a window test can be made robust to the display being in use (or should say so and report UNSUPPORTED), and that a test waiting on a capture should fail when the swapchain goes invalid instead of waiting for the wrapper's limit.
