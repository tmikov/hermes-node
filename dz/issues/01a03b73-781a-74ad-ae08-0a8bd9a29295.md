`kit.manifest` records absolute shared-library paths belonging to the machine
that cut the kit, and unlike `cc:` they are binding: the link fails on a
machine whose libraries sit elsewhere, naming a path the user never chose.

Every absolute shared library on CMake's link line is copied into `linkarg:`
verbatim. `utils/make-kit.py:230` classifies an argument as a system library
when its basename matches `SHARED_LIB_RE` (`\.(so|dylib|tbd)(\.\d+)*$`) and
appends it unchanged -- no `{kit}` substitution, no reduction to `-l`.

Verified against a real kit rather than inferred: a manifest cut from
`cmake-build-asan` contains exactly seven absolute paths, and after the `cc:`
work below, six of them are ICU:

```
linkarg: /usr/lib/x86_64-linux-gnu/libicuuc.so
linkarg: /usr/lib/x86_64-linux-gnu/libicui18n.so
linkarg: /usr/lib/x86_64-linux-gnu/libicudata.so
   (each repeated once, for the static-interdependency reason make-kit.py notes)
```

ICU is the only library that arrives this way on this tree; everything else
is already an `-l` flag.

**The `cc:` half of this issue is done** (`cbca3f1`). The recorded compiler
path is now the first *candidate* rather than a requirement -- resolution
falls back to its basename on `PATH`, then to `c++`, with `--cc` overriding
-- so an absolute `cc:` no longer binds a kit to one machine. This issue was
retitled to the half that is left.

**The fix is small: emit `-L<dir> -l<name>` in place of the absolute path.**
An earlier version of this issue claimed the directory was the hard part.
Measured, it is not:

- `c++ e.cpp -licuuc -licui18n -licudata` links with no `-L` whatsoever,
  because `/usr/lib/x86_64-linux-gnu` is already in the linker's default
  search path (`ld --verbose | grep SEARCH_DIR` lists it, along with
  `/usr/lib64`, `/usr/lib` and the rest).
- `-L/nonexistent/does/not/exist -licuuc` also links, exit 0 and no warning.
  A `-L` naming a directory that is not there is silently ignored.

So keeping the recorded directory as a `-L` costs nothing and is strictly
better than today in every case: it hits on a machine laid out like the
build machine, it is ignored on one where the library sits in a different
standard place and `-l` finds it there, and it still covers a build machine
whose ICU was in a custom prefix -- the one case where the path carried real
information. The only remaining failure is a target with ICU somewhere
non-standard, which fails today too, and fails today with a misleading path
rather than a clean `cannot find -licuuc`.

**Caveat for the static-ICU stopgap** on 01a03b73-c62a: `-l` prefers a
shared library, so a build that deliberately wants `libicuuc.a` has to name
it or use `-Bstatic`. That configuration is hypothetical today. It is a
reason to check the flag translation against a static build if that stopgap
is ever taken, not a reason to leave absolute `.so` paths in place now.

**Ordering still matters.** `make-kit.py` deliberately hoists system
libraries after every archive; whatever emits `-L`/`-l` must preserve that.

    Split confirmed 2026-08-26. This issue's two halves need different work and
    should probably become two issues when someone picks it up.

    **The `cc:` half is absorbed by 01a03b73-93a3.** Its agreed resolution order
    uses the recorded absolute path only as the first *candidate*, falling back to
    the basename on `PATH` and then to `c++`, with `--cc` overriding. That makes
    the recorded absolute path a hint rather than a requirement, which is the
    whole complaint. No work is needed here for that half.

    **The shared-library half stands and needs its own design round.** Turning
    `/usr/lib/x86_64-linux-gnu/libicuuc.so` into `-licuuc` is the obvious move,
    but it is only half an answer: something must decide what happens to the
    directory. A `-L/usr/lib/x86_64-linux-gnu` is barely less host-specific than
    the absolute path it replaced, and omitting it is only safe for directories
    already on the linker's default search path -- which means knowing that list,
    per platform and per linker. That is a real design question, not a
    transformation.

    **Context that raises the stakes.** A related idea -- record the driver's
    *expanded* link line and invoke `ld` directly, dropping the compiler
    requirement -- was explored and rejected for making exactly this problem
    worse. `clang++ -### h.o -o h` expands to five crt objects, eight `-L` paths,
    a `-dynamic-linker` path and `-lstdc++ -lm -lgcc_s -lgcc -lc`, with
    `crtbeginS.o` under a **gcc-version-stamped** directory
    (`/usr/lib/gcc/x86_64-linux-gnu/13/`). Baking that into the manifest trades
    "needs a C++ driver" for "needs an identical filesystem layout down to the
    GCC major version". Verified to work when run by hand, and still the wrong
    trade.

    The general principle the whole area should follow: **the kit binds the
    toolchain as late as possible.** The driver's real job is computing
    host-specific paths on the machine where the link happens; a manifest that
    pre-computes them defeats the one thing that makes a kit portable.

- 2026-08-26T03:53:36.265Z  Tzvetan Mikov <tmikov@gmail.com>  status: open -> closed (fixed)
    Fixed. `as_link_flags()` in `utils/make-kit.py` now records an absolute
    shared library as `-L<dir> -l<name>`, one `-L` per directory emitted ahead
    of the first library that needs it, since a `-L` applies only to the `-l`
    flags after it. Repeats are preserved -- ICU is listed twice on purpose for
    the static interdependency.

    A **versioned** soname is deliberately left absolute. `libfoo.so.5` cannot
    become `-lfoo`, which resolves through the `libfoo.so` development symlink
    that a machine carrying only the runtime package does not have. Nothing on
    this tree arrives versioned, so no line in a real manifest is affected, but
    the rule is in the code and in the test.

    **The manifest before and after**, cut from the same build:

    ```
    -linkarg: /usr/lib/x86_64-linux-gnu/libicuuc.so      (x2, and the same for
    -linkarg: /usr/lib/x86_64-linux-gnu/libicui18n.so     i18n and data)
    +linkarg: -L/usr/lib/x86_64-linux-gnu
    +linkarg: -licuuc
    +linkarg: -licui18n
    +linkarg: -licudata          (the trio repeated once, as before)
    ```

    **Verified by relocating the layout, not by reading the diff.** With the
    recorded `-L` pointed at `/some/other/distro/lib`, which does not exist --
    standing in for a machine whose ICU is somewhere else -- the link succeeds
    and the executable runs, because `-licuuc` finds the system copy through
    the linker's default search path. The same kit with the old absolute paths
    substituted back fails, hard:

    ```
    clang++: error: no such file or directory: '/some/other/distro/lib/libicui18n.so'
    error: /usr/bin/clang++ failed with exit status 1
    ```

    So the change fixes a real failure rather than a hypothetical one.

    **Test.** `test/make-kit-classify.js` drives `test/make-kit-classify.py`,
    which imports `make-kit.py` and checks the classification directly: the
    translation, one `-L` per directory, repeats preserved, existing `-l` flags
    untouched, a versioned soname left alone, a `.dylib` translated with a
    `-framework` pair kept intact, and a relative path left alone. It needs no
    kit, no hermes-node and no linker. `make-kit.py` had no test at all before
    this -- it runs only while cutting a kit, so a classification mistake used
    to surface at somebody else's link, which is the failure the manifest
    exists to prevent.

    The static-ICU caveat recorded earlier still stands and is unaffected: `-l`
    prefers a shared library, so if the stopgap on 01a03b73-c62a is ever taken,
    this translation needs rechecking against it.
