`test/build-exe-vm-options.js` checks the locked-executable refusal with

    // LOCKED: locked
    // LOCKED: --build-bundle --allow-vm-options-override
    // LOCKED: then link it again with: --build-exe

so the two-step remediation is covered as of the final review round. What is
NOT pinned is the wording of the first line itself:

    Error: this executable's VM options are locked and cannot be overridden.

Only the substring `locked` is asserted, which the bundle path's message also
contains. So an edit that made the executable print the *bundle* wording --
"this bundle's VM options are locked", telling someone to rebuild with
`--build-bundle` and stopping there -- would not fail any test, even though
the distinction is the whole reason the executable has its own message: a
produced binary has no `--vm=`, and unlocking it needs a container rebuild
AND a re-link.

One CHECK line for `this executable's` closes it.

Small, and noted rather than fixed because the branch it came from was already
squashed and green. Worth folding into whatever next touches that file.
