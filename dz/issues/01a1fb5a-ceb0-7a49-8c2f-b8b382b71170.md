While one event-delivery pass is running, every `resize` it delivers
allocates a new surface generation and no retired generation is destroyed.
If resize events keep arriving faster than the pass delivers them, the pass
does not end and the retired generations pile up.

**Not measured in a real program.** What was observed is a test, described
below; the rest is read from the code.

Mechanism, each point checked against the source:

- A `resize` event starts a new generation on the JS thread before that
  event's listeners run: `gTable->newGeneration()` followed by
  `gBackend->createGenerationSurfaces()` in
  `tools/hermes-node-ui/ui_module.cpp`.
- A retired generation is not destroyed where its last reference is
  dropped. The `SurfaceTable` destroy callback (same file) posts
  `destroyGeneration(gen)` to the `OwnerDispatch`, and a function posted
  while a drain pass is running runs in a later pass
  (`include/hermes/node-compat/compositor/owner_dispatch.h`, "Ordering").
- Event delivery is itself one posted function, `runEventDispatch`, which
  calls `uiDispatchEvents` (`tools/hermes-node-ui/ui_events.cpp`).
  `EventDispatcher::dispatch` (`lib/compositor/event_dispatcher.cpp`) keeps
  going "pass after pass until a drain comes back empty", so it returns
  only once the input queue is empty at the moment it looks. Until it
  returns, the `OwnerDispatch` pass it runs in has not ended, and none of
  the destroys posted meanwhile has run.
- On Metal the second half of reclamation cannot run either. Sokol releases
  a destroyed resource only in a later `sg_commit()`, and the commits that
  do it when nothing is drawing ("maintenance", `workerLoopTurn` in
  `lib/compositor-gpu/metal_backend.mm`) are issued from the loop's check
  phase, which is not reached while the delivery is still on the stack.

Observed on macOS (Task 16d) in `test/ui-metal-maintenance.js`, before the
test was changed to yield one loop turn (`setImmediate`) after each
`resize`: the in-process window driver applies a resize synchronously, the
test's `await` chain resumed inside the delivery of the previous `resize`,
and all twelve resizes ran inside one pass. Twelve generations were
allocated; the eleven destroys ran back to back after the pass ended. A
temporary trace in `OwnerDispatch::drainQueue` showed the pass boundaries.
The test now yields, so it no longer shows this.

A real program gets there with a `resize` listener that is slower than the
rate resize events arrive at, for example one that lays out and renders
synchronously during an interactive drag: the queue is never empty when the
dispatcher looks again.

Cost: each undestroyed generation is three framebuffer-size textures
(`kSlotsPerGeneration`). On Metal there is also a hard end: the producer's
id-pool guard in `createGenerationSurfaces` (`kIdPoolGuard`) refuses a new
generation once Sokol's pool runs low, and the resize path turns that
refusal into `terminateGraphicsSession`. How many resizes that takes has
not been measured.

GL is affected by the first half too: the destroy is posted the same way,
so the textures accumulate for the length of the pass. It has no id pool
and no deferred release, so the pool guard does not apply there.

Possible directions, none tried: bound the number of passes one
`dispatch()` call makes and re-post for the rest; coalesce queued resizes
so that one delivery pass starts at most one generation; or run pending
generation destroys between events rather than between `OwnerDispatch`
passes.
