`libjs/setup-stdio.js` gives a TTY a `tty.WriteStream`, a libuv stream whose
writes are queued, where node writes stdio synchronously on POSIX for a TTY
or a file. CLAUDE.md records that in the context of `process.exit()` losing
output; this issue is about the other consequence, which is visible while the
program is still running.

Found while building `examples/ink`. A TUI redraws a frame as one burst of
escape sequences and text. Under node that burst reaches the terminal
synchronously; here it can be interleaved with other output -- notably a key
echoed by the tty before the program's own `setRawMode()` has taken effect --
so a frame can appear torn mid-redraw. Node does not show this because its
write lands before the next thing can get in.

The example works around it rather than depending on it: its
node-versus-hermes-node byte comparison sends no keystroke, and its keypress
checks grep for a fixed marker instead of comparing the whole stream. See
`examples/ink/README.md` for the write-up.

Two things this is NOT: it is not a grapheme segmentation problem
(`Intl.Segmenter` output is byte-identical to node's), and it is not
Ink-specific -- anything drawing a frame to a raw-mode terminal is exposed.

What a fix probably means: writing synchronously to a TTY on POSIX the way
node does, rather than routing through a libuv stream, at least for the
fd-is-a-tty case. That is the same underlying change the `process.exit()`
flush note in CLAUDE.md gestures at ("draining the stdio write queues
specifically would be the better fix"), so the two are worth solving
together.
