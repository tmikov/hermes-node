A produced executable requires glibc 2.38, which rules out Debian 12 (2.36),
RHEL 9 (2.34) and Ubuntu 22.04 (2.35). Nothing about the program needs
anything that new. Part of 01a03b73-c62a, split out because the fix is a
release-CI change and shares nothing with the ICU half.

**No linker flag can fix this.** Symbol versions are bound against the host's
`libc.so` at link time, so it is decided by the machine that links, not by
how much is linked statically. Measured: an executable built with static ICU
and `-static-libstdc++ -static-libgcc`, whose only remaining shared
dependencies are glibc itself, still requires GLIBC_2.38.

**The floor is accidental.** Everything above 2.34 comes from five symbols:

```
(GLIBC_2.36) arc4random, arc4random_buf
(GLIBC_2.38) __isoc23_strtoul, __isoc23_strtoull, fmod
```

`__isoc23_strtoul` is glibc's C23 redirect of a plain `strtoul` call -- a
header decision, not an API we asked for. The 2.38 `fmod` is a
more-accurate variant of the same function; linking against an older glibc
binds the older one, and nothing here depends on the difference. Only
`arc4random` is a deliberate API choice, and it is the cheaper of the two to
avoid. Everything else the binary imports sits at 2.34 or below -- the 2.34
cluster is just `__libc_start_main`, `dlopen` and the `pthread_*` family,
which all moved into libc at 2.34 and resolve to lower versions when linked
on an older system.

So building against a glibc 2.34 baseline would plausibly cover RHEL 9,
Debian 12 and Ubuntu 22.04 with no source change beyond `arc4random`.

**The fix is a build-baseline change**: link release artifacts in a
manylinux-style container, or on the oldest distribution we intend to
support. That is `.github/workflows/release.yml` plus a container image, not
C++.

**Full `-static` is not an alternative, and is ruled out on its own merits.**
`hermes-node` `dlopen`s `.node` addons. Measured twice: the linker warns that
`dlopen` in a static binary "requires at runtime the shared libraries from
the glibc version used for linking", which reintroduces the dependency the
static link was meant to remove; and the addon is itself a shared object
needing `libc.so.6` and `ld-linux` (checked against
`cmake-build-asan/hello_addon.node`). A runtime that loads native addons
needs a dynamic glibc present. Static glibc is also LGPL-encumbered in a way
static libstdc++ is not, which is worth a real check if it is ever
reconsidered.

    Revisited 2026-09-03, now that ICU is gone and this is the only barrier.
    The conclusion holds, but the reasoning under it was incomplete in a way
    that makes the fix look harder than it is.

    **Every symbol above 2.34 is an artifact of the build environment. None is
    a choice this project made, and no source change is needed for any of
    them.** Re-derived from a current artifact (six, not five -- the list below
    supersedes the one in the body):

    | symbol | ver | why it is there |
    |---|---|---|
    | `_dl_find_object` | 2.35 | only with `-static-libgcc`; the unwinder in the host's libgcc |
    | `arc4random` | 2.36 | `HAVE_DECL_ARC4RANDOM`, a `check_symbol_exists` in llvh |
    | `arc4random_buf` | 2.36 | `HAVE_ARC4RANDOM_BUF`, a configure check in c-ares |
    | `__isoc23_strtoul` | 2.38 | glibc header redirect of a plain `strtoul` call |
    | `__isoc23_strtoull` | 2.38 | same |
    | `fmod` | 2.38 | the 2.38 variant, bound at link time |

    The `arc4random` pair are feature-detected with working fallbacks already in
    the tree: llvh falls back to `srand`/`rand`
    (`external/llvh/lib/Support/Unix/Process.inc:455`), and c-ares to
    `getrandom` -- whose `HAVE_GETRANDOM` is already 1 in our generated
    `ares_config.h`, so it does not even fall as far as the file-backed path.
    This corrects the body above, which called `arc4random` "a deliberate API
    choice" and the more expensive of the two to avoid. It is neither; it
    costs nothing because nobody chose it.

    `__isoc23_*` is a header decision, and specifically not one we can switch
    off. `features.h` turns `_GNU_SOURCE` into `_ISOC2X_SOURCE`, that into
    `__GLIBC_USE_ISOC2X`, and that into `__GLIBC_USE_C2X_STRTOL`, which makes
    `stdlib.h` redirect `strtol` and friends by `__asm__` name. Defining
    `__GLIBC_USE_C2X_STRTOL=0` on the command line does not work --
    `features.h:154` `#undef`s it first. Dropping `_GNU_SOURCE` is not on the
    table.

    So building against an older glibc fixes all six at once and automatically,
    because each one is a detection that would resolve the other way there.
    That is a stronger argument for the build-baseline fix than the body makes:
    it is not "the cheapest of several remedies", it is the only one that needs
    no code.

    **The kit bakes the floor in, which couples this to 01a03b73-dcef.**
    `__isoc23_strtoul` and `__isoc23_strtoull` are literal undefined symbol
    names inside `libhermes-node-kit.a`, put there when the kit was compiled --
    unlike `fmod` and `arc4random`, whose version is chosen at the final link.
    A machine with glibc < 2.38 therefore cannot *link* against a kit cut on
    this machine at all; it fails with an undefined symbol before anything
    runs. So if a release ever ships a kit, that kit must be cut in the same
    old container as the binary, or we export our floor to every executable
    any user ever produces.

    **Release artifacts are currently worse than this issue records.**
    `.github/workflows/release.yml` builds `build-linux` on `ubuntu-latest`,
    which is 24.04 and glibc 2.39. The 2.38 figures here and in 01a03b73-c62a
    come from a local build; a released binary is a notch higher.

    **Untested.** There is no container runtime on this machine, so the claim
    that an older image resolves these the other way is reasoned from the
    detection code and the glibc headers, not measured. Whoever does this
    should verify the resulting floor rather than assume it, and should check
    that clang-18 is installable in whatever image is chosen.

    Full Release build of the `hermes-node` target inside
    `docker.io/library/almalinux:8`, source bind-mounted read-only, output to a
    separate directory, `-DHERMES_NODE_VERSION` pinned so nothing needs git.
    Configure and build both clean, first try, no source changes.

    Only two versioned imports at or above 2.25 survive:

    ```
    GLIBC_2.25   getrandom
    GLIBC_2.28   fcntl64
    ```

    Everything else is 2.23 or lower. No `__isoc23_*` and no `arc4random` of
    either spelling -- both predicted by the previous comment, both confirmed.
    `getrandom@2.25` is *literally* the c-ares fallback that analysis said
    `HAVE_ARC4RANDOM_BUF=0` would select, so the mechanism is confirmed by the
    symbol that replaced it, not just by the absence of the old one.

    **`fcntl64` alone sets the floor.** It is glibc 2.28's LFS `fcntl` export,
    nothing this project chose. An older image would drop below 2.28; there is
    no reason to, since 2.28 is Node's own Tier 1 x64 requirement
    (`BUILDING.md`: kernel >= 4.18, glibc >= 2.28, "e.g. Ubuntu 20.04, Debian
    10, RHEL 8").
