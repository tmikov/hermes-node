Minor test-quality items from the final whole-branch review of the Wasm
compile cache (2026-09-07). Neither is a bug; both are tests that pass
whether or not the thing they name is working.

**`WasmCache_TooSmallStructIsRejected`**
(`hermes/unittests/napi/NapiWasmCacheTest.cpp`) was written for the fix in
`683eb9bb6`, which moved `hermes_set_wasm_cache`'s `struct_size` check ahead
of the dereferences it guards. But the test sets a small `struct_size` on a
*fully sized* object, so no out-of-bounds read occurs either way and the
test passes with or without the fix. Catching the original defect needs a
genuinely truncated allocation.

**The accepting half of the same check is untested.** `683eb9bb6` also
changed `!=` to `>=`, so a caller from a newer header with a *larger*
`struct_size` is accepted and only the known fields are read. Nothing
exercises that path.

Also noted, in the same file: `FakeCache::lastConfig` is recorded and never
asserted. The end-to-end coverage for `codegen_config` now exists on the
hermes-node side (`test/test-wasm-cache.js` runs a file plain and with
`--vm=-test262` and requires four entries rather than two), so this is
redundancy rather than a gap -- but the unused member should either be
asserted or removed.

    Fixed in the hermes submodule, commit 5210f4f12 on wasm-compile-cache.

    The issue's claim was verified rather than taken on trust, in both
    directions. With the pre-fix ordering restored (the struct_size check moved
    back after the callback reads), WasmCache_TooSmallStructIsRejected still
    PASSES -- it cannot catch the bug it was written for, exactly as recorded.

    WasmCache_TrulyTruncatedStructIsNotReadPastItsEnd now allocates exactly what
    an old caller owns -- through struct_size and ctx, not a byte further -- so
    an early read of `lookup` is a genuine out-of-bounds. With the same pre-fix
    ordering it fails, AddressSanitizer reporting a heap-buffer-overflow READ of
    size 8 at that line. It discriminates.

    WasmCache_LargerStructIsAccepted covers the accepting half, which had no
    test at all: a newer caller's larger struct_size must be accepted, only the
    known fields being read, which is what makes the ABI extensible. Tightening
    the comparison back to != fails it, so it discriminates too. It asserts the
    cache was actually installed and used, not merely that the call returned ok.

    The original test is kept: proving a small size is rejected is worth having
    on its own, it simply never proved the memory-safety half.

    The issue's third item, FakeCache::lastConfig being recorded and never
    asserted, was already resolved when codegen_config became an opaque byte
    string -- WasmCache_MissCompilesAndStores now asserts the blob's content,
    by substring rather than exact match since it is designed to grow.
