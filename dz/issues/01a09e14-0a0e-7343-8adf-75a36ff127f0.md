The require() scanner builds a bare `hermes::Context`
(`lib/bundle/require_scanner.cpp:424`), whose defaults are
`enableAsyncGenerators_{false}` and `enableES6BlockScoping_{false}`
(`hermes/include/hermes/AST/Context.h:276,281`). Only `setParseTS` is
configured. The bytecode compile step it feeds sets both to true
(`hermes/API/napi/hermes_napi_compile.cpp`, `enableES6BlockScoping = true`,
`enableAsyncGenerators = true`).

Async generators are the visible half, because without the flag they are a
**parse** error rather than a semantic difference. So the scanner rejects any
module containing `async function*`, and the producer packages it as a
module that throws when required -- a file the compiler right behind it would
have compiled without complaint.

Reproduced against cmake-build-release:

    $ cat gen.js
    async function* g() { yield 1; }
    module.exports = g;
    $ cat app.js
    const g = require("./gen.js");
    (async () => { for await (const v of g()) console.log("PASS", v); })();

    $ hermes-node app.js
    PASS 1

    $ hermes-node --build-bundle=app.hbb app.js
    warning: cannot parse /tmp/agbug/gen.js (1:60: async generators are
    unsupported); packaged as a module that throws when required

    $ hermes-node --bundle=app.hbb
    SyntaxError: /tmp/agbug/gen.js: 1:60: async generators are unsupported

So a program that runs is silently turned into one that does not, and the
only notice is a build-time warning that reads like the file is at fault.

The comment at `require_scanner.cpp:437-442` states the invariant that is
broken: "a failure here means the compiler will reject the same wrapped text
for the same reason, so treating it as a scan failure is not a new
restriction." That is exactly what does not hold -- the scanner is strictly
stricter than the compiler it speaks for.

ES6 block scoping is the other half and is not known to reject anything; with
it off, `let`/`const` resolve without per-iteration bindings. That changes
semantics rather than acceptance, so it cannot mis-stub a module, but it does
mean the scanner resolves bindings under different rules than the compiler,
which is worth closing at the same time since it is the same line of code.

Fix: configure the scanner's `Context` from the same flags the compile step
uses, and keep the two in one place so they cannot drift again. A regression
test belongs beside `test/bundle-tolerant.js`: a module using an async
generator must survive `--build-bundle` and run, not be stubbed.

Found while reviewing the native-compilation design
(`docs/superpowers/specs/2026-09-13-native-compilation-design.md`), which
needs the same flag parity for `shermes` and now records this scanner
divergence as a prerequisite. It is a pre-existing defect in the bytecode
producer, independent of that work.
