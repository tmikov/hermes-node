The Linux release tarball now carries a kit, so `--build-exe` works from a
release there (01a03b73-dcef). macOS still ships none, and the reason is
specific rather than "not done yet".

A macOS kit would be **universal**: the release job configures
`CMAKE_OSX_ARCHITECTURES="x86_64;arm64"`. CLAUDE.md records the trap that
makes this the one configuration nobody has verified end to end: `ld -r`,
`libtool` and `lipo` each emit a valid-looking **empty slice** for a missing
architecture -- warnings only, exit status 0, and `lipo -info` reports the
slice as real. It surfaces at the *user's* link, as an undefined `_main`.

The check that makes Linux safe does not transfer. There, the release job
builds a real executable with the staged kit and runs it; on macOS the runner
is arm64, so the same test would exercise one slice and say nothing about the
other. A kit that works for half its audience and fails opaquely for the rest
is worse than shipping none, which is why this is split out rather than
bundled into the Linux change.

What it needs, per CLAUDE.md's own rule for whatever cuts a universal kit:
**assert per-slice symbol counts and never trust exit status.** Concretely, a
release step that runs `lipo -info` plus a per-architecture `nm` count over
each archive in the kit and fails on an empty or implausibly small slice, and
ideally a cross-arch smoke test rather than only the runner's native one.

`utils/make-kit.py` already warns loudly, by architecture, when the link line
it is handed names more than one -- deliberately a warning and not an error,
so it does not block macOS releases to report something that may well be
fine. That warning is the starting point, not the solution.

Note the `libtool -static` branch of `make-kit.py` has never executed
anywhere; the macOS spike predates the script. So this work also covers the
first real exercise of that path.
