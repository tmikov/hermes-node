`--build-exe` generates a `.s` holding the container as an `.incbin` and runs
it through the C++ driver to get an object file
(`payloadAssembly()` and `buildAssembleCommand()` in
`lib/build-exe/build_exe.cpp`). The driver is there only to forward target
flags such as `-arch`; the actual work is an assemble of a file we generated
ourselves and whose entire content we control.

Emitting the object directly would delete the step, and with it half the
toolchain requirement: what remains is a link, which is the dependency the
design already accepted.

This is more reachable than it sounds. `ObjectFormat` is already a parameter
rather than an `#ifdef`
(`include/hermes/node-compat/build-exe/build_exe.h`), so both spellings are
already compiled on every host, and the existing code already reasons at the
object-format level -- `.p2align 4` for `kBundlePayloadAlign`,
`MH_SUBSECTIONS_VIA_SYMBOLS` on Mach-O, and the mandatory
`.section .note.GNU-stack,"",@progbits` on ELF, without which the linker marks
the whole program `GNU_STACK RWE`. An emitter has to get those same three
things right, in a place where they are checked by construction rather than by
a string in a generated file.

What it buys beyond dropping the dependency: the quoted-path hazard disappears.
Today the container path is interpolated into an assembler string literal, so
it must be made absolute and rejected if it contains `"`, `\`, CR or LF,
because GAS resolves escapes inside the path. An emitter writes bytes and a
symbol; there is no lexer to defend against.

Prerequisite for judging effort: how much of a minimal ELF `.o` and Mach-O `.o`
we would have to hand-roll -- one section, two symbols (`start`/`end`), correct
alignment, correct stack note. Worth a spike before committing to it.
