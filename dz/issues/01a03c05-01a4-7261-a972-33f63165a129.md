On Linux, Hermes reaches ICU for exactly four JavaScript features, and that
one dependency is what stops a produced executable from running anywhere
lacking `libicu*.so.74`. The soname is an exact match, not a minimum, so it
excludes older distributions and newer ones alike (umbrella:
01a03b73-c62a).

**The whole surface is fifteen functions.** Measured with
`nm -D --undefined-only` on `bin/hermes-node`:

| ICU functions | JS feature |
|---|---|
| `u_strToLower`, `u_strToUpper` | `String.prototype.toUpperCase` / `toLowerCase` |
| `unorm2_getNF{C,D,KC,KD}Instance`, `unorm2_normalize` | `String.prototype.normalize` |
| `ucol_open`, `ucol_close`, `ucol_setAttribute`, `ucol_strcoll` | `String.prototype.localeCompare` |
| `udat_open`, `udat_close`, `udat_format`, `uloc_getDefault` | `Date.prototype.toLocaleString` and friends |

For those fifteen we link 41 MB of ICU (29.4 MB of it `libicudata.a`).

**Only two of the four are actually pinned by the spec.** This build has
`HERMES_ENABLE_INTL=OFF`, and without ECMA-402 both `localeCompare` and
`Date.prototype.toLocaleString` are implementation-defined: any consistent
total order, any format. Case conversion (Unicode Default Case Conversion)
and `normalize` (UAX #15) are the two that must be right.

**It is a Linux-only problem.** The `PlatformUnicode` layer is CoreFoundation
on Apple (`PlatformUnicodeCF.cpp`) and Java on Android; those are real
implementations from the OS, which is why a macOS binary needs no
third-party library at all. Linux has no system equivalent.

**`HERMES_UNICODE_LITE` is not the escape hatch it looks like.** The option
exists and takes the same "no ICU" path Apple does, but its implementation
(`PlatformUnicodeLite.cpp`, 55 lines) is stubs: `convertToCase` has an empty
body, so `"abc".toUpperCase()` returns `"abc"`; `normalize` is empty;
`dateFormat` returns the literal string `"dateFormat not implemented"`. Only
`localeCompare` is real, as a code-unit comparison. That is silent breakage
across enormous amounts of ordinary code, not a trade-off.

**The precedent for doing this properly is already in the tree.** Hermes
implements regex `/i` case folding with no ICU at all: `canonicalize()` in
`hermes/lib/Platform/Unicode/CharacterProperties.cpp` reads generated tables
from `UnicodeData.inc`, and simple case folding for the whole of Unicode is
**206 range entries** in a compact range+transform encoding. The generator,
`hermes/utils/genUnicodeTable.py`, is in the tree too.

`toUpperCase`/`toLowerCase` is the same shape of problem -- different
mappings than folding, plus a small special-casing table for multi-character
cases such as the German sharp s uppercasing to SS. Normalization is the
genuinely harder one and its table size has NOT been measured; do that before
committing to a plan. The two implementation-defined features need nothing
clever: a code-unit order and a `strftime`-based format are both spec-legal.

**Decided 2026-08-26: worth doing, not now.** The fix lands in the Hermes
submodule rather than this repo, which is why this is filed under the
`hermes` component. The alternatives were weighed on 01a03b73-c62a: static
ICU costs +36 MB per artifact and changes no behaviour, and trimming ICU's
data (what Node's "small-icu" does) needs us to build ICU ourselves.

    shape of `canonicalize()`/`UnicodeData.inc`, one set per feature.

    | replaces | new code |
    |---|---|
    | `u_strToLower`, `u_strToUpper` | `UnicodeCaseConversion.cpp` + `CaseData.inc` (448 lines) |
    | `unorm2_*` | `UnicodeNormalization.cpp` + `NormalizationData.inc` (3780) |
    | `ucol_*` | `UnicodeCollation.cpp` + `CollationData.inc` (6041, DUCET / UTS #10) |
    | `udat_*`, `uloc_getDefault` | `PlatformDateFormat.cpp`, a fixed formatter |

    `PlatformUnicodeICU.cpp` is deleted. Linux and Windows get a new backend,
    `PlatformUnicodeHermes.cpp`. Both conformance suites came with it (UAX #15
    normalization, UCA collation).

    **Verified on this tree, not taken on faith.** After rebuilding

    - `nm -D --undefined-only bin/hermes-node | grep -Ei 'u_str|unorm2|ucol_|udat_|uloc_'`

    - `ldd bin/hermes-node` -> `libm libstdc++ libresolv libgcc_s libc ld-linux`.
      No `libicu*`. Same for a `--build-exe` artifact.
    - `check-hermes-node` green: 333 unit, 192 JS, 0 failures, 0 unsupported.
    - Spot checks: NFD/NFC of "A-ring" give 2 and 1 code units; `"strasse"` with

      orders `a, a-umlaut, b`, so the collation really is UCA rather than code
      units.

    **Two corrections to the body above.**

    `HERMES_UNICODE_LITE` is no longer stubs. `PlatformUnicodeLite.cpp` now calls
    the same tables every other backend does, so the "silent breakage across
    enormous amounts of ordinary code" warning is obsolete.

    The two implementation-defined features did not take the cheap answer this
    issue sketched as sufficient. `localeCompare` is real DUCET root collation,
    not a code-unit order, and `dateFormat` is a purpose-built fixed formatter
    rather than `strftime`.

    **One behaviour change worth knowing about.** Date formatting is now
    locale-independent: `toLocaleString`, `toLocaleDateString` and
    `toLocaleTimeString` produce identical output under `LANG=en_US.UTF-8`,
    `de_DE.UTF-8` and `tr_TR.UTF-8` (`Jan 2, 2020, 3:04:05 PM`). That is
    spec-legal with `HERMES_ENABLE_INTL=OFF` and this issue anticipated it, but
    it is a visible difference for anyone who was getting localized dates out of
    the ICU build.

    Casing, by contrast, still honours the host locale: with
    `LC_ALL=tr_TR.UTF-8`, `"i".toLocaleUpperCase()` is the dotted capital and
    `"I".toLocaleLowerCase()` is the dotless small i. `computeHostCaseLocale()`
    in `PlatformUnicodeHermes.cpp` replicates ICU's `uloc_getDefault` variable
    order (`LC_ALL`, `LC_MESSAGES`, `LANG`), deliberately ignoring `LC_CTYPE`
    because ICU ignored it too.

    Downstream: 01a03b73-c62a loses its ICU half entirely, and 01a03c05-2967
    (the glibc floor) becomes the only thing pinning a produced Linux executable
    to its build machine.
