`--build-exe` cannot work on a released `hermes-node`, because no release
contains the kit it links against.

`.github/workflows/release.yml` stages the binary alone -- `cp
build/bin/hermes-node "staging/${NAME}/"` on both the Linux and macOS jobs --
and there is no `install()` rule for the kit in
`tools/hermes-node/CMakeLists.txt`. `resolveKitDir()` looks beside the running
binary, finds no `kit.manifest`, and the verb fails there.

So for anyone who did not build from source, the feature does not exist. That
is the reason the other build-exe issues matter: fixing the manifest's absolute
paths makes a kit portable between machines, but nobody outside this repo has a
kit at all.

CLAUDE.md records this as deliberate and unmade rather than overlooked: a
Release kit is ~40 MB against a binary of a few MB, so shipping one is a product
decision about download size. That decision is what this issue is for. Options,
roughly in increasing cost:

- Ship the kit as a **separate** release asset, so `--build-exe` users download
  it and nobody else pays.
- Ship it in the main tarball and accept the size.
- Leave it source-only and say so in the docs, which at least stops the feature
  from looking available when it is not.

Whatever is chosen, note the kit is invalidated by every commit: `kit.manifest`
pins the `git describe` version and the consumer compares it for exact string
equality. A release kit and its binary must therefore be cut from the same
build, which is an argument for doing it in the release workflow rather than by
hand.
