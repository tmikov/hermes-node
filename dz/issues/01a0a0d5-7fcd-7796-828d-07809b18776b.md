A native build's stack traces are asserted through
`test/build-native.js`, which pins the CURRENT behaviour rather than the
desired one: the plain `e.stack` string is correct at `-g2` (it carries
`identity:line:column`, threaded through `-source-name=<identity>` on the
shermes command line), but `Error.captureStackTrace`'s structured
`CallSite` objects -- `getFileName()`, `getLineNumber()`,
`getColumnNumber()` -- return null at every `-g` level, native or not.

This is a Hermes limitation, not something native compilation introduced;
it is more visible here because build-native's whole pitch is that a
native artifact behaves like the bytecode one it replaces, and the two
mechanisms (source string vs. structured CallSite) diverge in how much
location data they carry through to a native binary.

A fix means finding where CallSite's backing frame data is populated and
teaching it to look up the same debug info the string-based %s path
already resolves. `test/build-native.js`'s existing assertions would need
updating alongside any fix, since they currently assert the null-location
behaviour is what happens.
