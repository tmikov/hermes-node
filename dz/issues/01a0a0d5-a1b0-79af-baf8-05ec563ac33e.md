Every `build-native` invocation recompiles every discovered module from
scratch: no cache keyed on source content or path, unlike the disk
compile cache the bytecode path gets for free. Measured on
`examples/flow-bundler`'s ~1,500-module substitute graph (see
docs/superpowers/plans/progress-native-compilation.md): a from-scratch
build takes about 460 seconds wall clock on a 16-core machine with
--jobs=16, all of it shermes-then-cc work per module, none of it reusable
across runs.

The design doc flagged an object cache as the natural follow-up work
rather than something this plan implements (see the "Measurements"
section's discussion of the per-file net.js numbers, where the C compile
dominates shermes's own time by roughly 24x) -- caching compiled objects
keyed on source content plus the codegen configuration (mirroring how the
disk compile cache's Wasm tier is keyed) would let repeated builds of an
unchanged dependency tree (the common case: only the entry or one
module changed) skip almost all of the work.

Filed from Task 16 of the native-compilation plan.
