`HERMES_NODE_ENABLE_UI` defaults to OFF and the release workflows
(`.github/workflows/release.yml`) do not turn it on, so no release
carries `hermes-node-ui` or the Dear ImGui addon
(`hermes-node-imgui.node`). The addon's design
(`docs/superpowers/specs/2026-11-27-imgui-addon-design.md`, Non-goals)
leaves "shipping the addon in one" as a separate decision, and nothing
else records it.

Questions a decision has to answer:

- Whether a release ships `hermes-node-ui` at all, on which platforms
  (the macOS window tests need a display, which CI runners may lack:
  01a1fbb5-84ef).
- The addon is found by its position beside the executable
  (`tools/hermes-node-ui/named_addons.cpp`), so a release archive must
  keep `hermes-node-imgui.node` in the same directory as `hermes-node-ui`.
- The addon resolves every `sg_*` symbol against the host when it is
  loaded, so the two must come from one build; `HNUI_CHECK_VERSION` refuses
  a mismatch at load time but packaging should make it impossible.
- `--build-exe` for UI programs is out of scope for the addon's design;
  whether a produced executable could find the addon is untested.
- `THIRD_PARTY_LICENSES.md` already lists ImGui.

Done when the decision is made and recorded, and either the release
workflows build and stage the UI binary and addon with a check that
`require('hermes-node:imgui')` works from the unpacked archive, or the
decision not to ship is written down here.
