`check-hermes-node` is red on this machine at the end of Task 7 (2026-09-25), before any Task 8
change, and this is the only failing test.

    unittests/CompositorTest.cpp:312
    Expected: (taken.load()) > (1000), actual: 166 vs 1000
    the threads must have raced for real

Measured, not inferred:

- `check-hermes-node-unit` (lit, parallel): FAILS 3 runs out of 3, always
  this test and only this test, 398 passes + 1 failure each time.
- The same lit suite with `-j1`: 399/399 PASS.
- The test binary alone, --gtest_filter on just this test: 6/6 PASS.

So it is not occasional. Under load it fails every time; alone it passes
every time. Task 7's progress note records 399/399 green, so the margin was
already thin and has tipped rather than newly broken.

## Why it fails

The assertion is a throughput floor inside a fixed wall-clock window: the
test lets four threads drift for 750 ms and then requires `taken > 1000`.
Under lit's parallelism the gtest binaries share the machine, this test's
threads get a fraction of the CPU they get alone, and 166 takes is what the
window buys.

That makes it a timing-based assertion, which the compositor plan's own
Global Constraints forbid for exactly this reason ("the suite runs 16-way
parallel"). The invariant the test exists for is the end-state check below
the assertion -- a displaced slot with a read outstanding must not be
stranded -- and that part is sound and load-independent. Only the progress
floor in front of it is load-sensitive.

## What it costs

It sits ahead of every commit: the plan requires a full `check-hermes-node`
before each one, and this makes that permanently red on any machine that
runs the suite in parallel. CI runs `check-hermes-node` with
`HERMES_NODE_ENABLE_UI=ON` in the asan-debug-o1 job, so CI is exposed too.

## Not fixed here

Found while executing Task 8, which touches nothing this test compiles.
The fix is a decision rather than a tweak: bound the work by a count of
completed cycles rather than by elapsed time, so the test does as much work
as it needs and takes as long as the machine makes it take. Raising the
window or lowering the floor trades one arbitrary number for another and
will tip again.

01a0629b-a94a (test-repl-history.js flake at 8-way).
