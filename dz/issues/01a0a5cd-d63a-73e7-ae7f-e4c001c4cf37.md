A `build-native` artifact with the default native built-ins carries exactly
one Hermes bytecode blob per architecture slice, and it is not ours:
`ExtensionsBytecode.hbc`, 1,680 bytes, built from
`hermes/API/hermes/extensions/*.js` (the `00-header.js` IIFE, `10-TextEncoder.js`,
`11-Worker.js`, `20-Dummy.js`, `99-footer.js`) and embedded as a C array by
`hermes/API/hermes/extensions/CMakeLists.txt`.

Nothing in this repository can reach it. It is run at every runtime creation
by `loadAndInstallExtensions()`, called from
`facebook::hermes::makeHermesRuntime` under `HERMES_ENABLE_CORE_EXTENSIONS`
(`hermes/API/hermes/hermes.cpp:1556-1558`), which
`lib/runtime/hermes_node_runtime.cpp:813` calls to build the runtime. So a
"fully native" artifact still links the Hermes bytecode interpreter and
still runs the compiler-free bytecode path once at startup, for 1,680 bytes
of JavaScript.

It is the sole reason `test/build-native-builtins.js` asserts
`MAGIC <slice> 1` rather than 0. That assertion is the headline claim of the
native built-ins work ("no built-in JavaScript is interpreted"), and the 1
is a standing asterisk on it.

Turning `HERMES_ENABLE_CORE_EXTENSIONS` off is not the fix: the same
mechanism installs `TextEncoder`, so declining the interpretation would
remove a global from every hermes-node build and every artifact.

The fix belongs in Hermes and is shaped exactly like the one Task 1 of the
native built-ins plan turned on for `InternalJavaScript`: compile the
concatenated extensions JS with `shermes -emit-c -exported-unit=...` into a
`hermesExtensionsUnit` target, keep the bytecode form building so it cannot
bitrot, and pick between the two with an alias, as
`hermes/lib/InternalJavaScript/CMakeLists.txt:55-59,98-103` already does for
`hermesInternalJavaScript_obj`. Extensions are installed through a JS
function the native side calls with native helpers, so the unit's exported
init is the same shape `loadAndInstallExtensions` already drives.

Cost of doing nothing: an artifact keeps one interpreted module, and the
count the test pins stays 1. Fixing it makes that 0, which is a test change
as well as a Hermes change.
