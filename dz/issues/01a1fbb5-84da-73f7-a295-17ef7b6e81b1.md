On macOS a request to quit the application reaches
`-[HnuiApplication terminate:]` (`tools/hermes-node-ui/mac_app.mm`), which
never calls AppKit's and forwards the request to the JS thread as a
cancelable `close` event. That is deliberate: AppKit's `terminate:` ends
the process from the main thread, bypassing `close` listeners and the
program's exit status.

The consequence for logout, restart and shutdown, which ask each
application to quit and wait:

- If no listener cancels and the JS thread is free, the JS thread ends the
  process within a loop turn and the logout continues.
- If a `close` listener cancels, the application stays, and the system
  waits until its own timeout and then reports that the application
  interrupted the logout.
- If the JS thread is busy in synchronous code, the same happens: the
  request sits in the input queue.

A close request carries no reason, so a program cannot tell a logout from
Quit and choose not to cancel.

**None of this was observed.** It is reasoned from the override and from
AppKit's documented behaviour; no logout was performed against a
`hermes-node-ui` program, and whether a logout's request reaches the
override at all is part of the unproved path in the issue about a real
Dock Quit.

The alternative considered and rejected, `applicationShouldTerminate:`,
is worse for this case: it must answer `NSTerminateCancel` to keep the
decision on the JS thread, and that cancels the logout outright.
`NSTerminateLater` with `replyToApplicationShouldTerminate:` is the AppKit
mechanism made for an asynchronous answer and was left out of scope; it
would need the reason-less `close` event to gain a way to answer later.
