`--build-exe` generates a `.s` holding the container as an `.incbin` and runs
it through the C++ driver to get an object file
(`payloadAssembly()` and `buildAssembleCommand()` in
`lib/build-exe/build_exe.cpp`). The driver is there only to forward target
flags such as `-arch`; the actual work is an assemble of a file we generated
ourselves and whose entire content we control.

Emitting the object directly would delete the step, and with it half the
toolchain requirement: what remains is a link, which is the dependency the
design already accepted.

This is more reachable than it sounds. `ObjectFormat` is already a parameter
rather than an `#ifdef`
(`include/hermes/node-compat/build-exe/build_exe.h`), so both spellings are
already compiled on every host, and the existing code already reasons at the
object-format level -- `.p2align 4` for `kBundlePayloadAlign`,
`MH_SUBSECTIONS_VIA_SYMBOLS` on Mach-O, and the mandatory
`.section .note.GNU-stack,"",@progbits` on ELF, without which the linker marks
the whole program `GNU_STACK RWE`. An emitter has to get those same three
things right, in a place where they are checked by construction rather than by
a string in a generated file.

What it buys beyond dropping the dependency: the quoted-path hazard disappears.
Today the container path is interpolated into an assembler string literal, so
it must be made absolute and rejected if it contains `"`, `\`, CR or LF,
because GAS resolves escapes inside the path. An emitter writes bytes and a
symbol; there is no lexer to defend against.

Prerequisite for judging effort: how much of a minimal ELF `.o` and Mach-O `.o`
we would have to hand-roll -- one section, two symbols (`start`/`end`), correct
alignment, correct stack note. Worth a spike before committing to it.

    Closing wontfix after a brainstorm that measured the premises. Every number
    below is from this machine (binutils 2.42, clang 18, g++ 13.3, glibc 2.39);
    reopen if any of them stops holding.

    **The stated payoff does not exist.** The issue said dropping the assembler
    leaves "a link, which is the dependency the design already accepted". True,
    but the link runs `manifest.cc` -- a C++ driver -- so removing the assemble
    step removes one of the driver's two uses, not the requirement. A user needs
    the same tool installed either way.

    **Speed is not a motivation.** Measured on a payload of the size these
    actually are:

    | payload | `clang -c` on `.incbin` | `ld -r --format=binary` + `objcopy` |
    |---------|------------------------|--------------------------------------|
    | 2.5 MB  | 16 ms                  | 8 ms                                 |
    | 50 MB   | 48 ms                  | 68 ms                                |

    It crosses over: the two-process route reads and writes the payload twice.
    Both are noise beside the link.

    **`ld -r --format=binary` was evaluated and rejected on its merits.** It
    produces the wrong thing four ways: symbols named from the mangled input path
    (`_binary__home_..._app_hbb_start`), a writable `.data` section rather than
    `.rodata`, alignment 1 where `openEmbeddedBundle` requires
    `kBundlePayloadAlign`, and no `.note.GNU-stack` -- which I linked and
    confirmed yields `GNU_STACK RWE`, the exact regression the current `.s`
    exists to prevent. One `objcopy` pass repairs all four (verified end to end),
    but it is ELF-only -- ld64 has no `--format=binary` -- so it splits the
    platforms rather than unifying them. It also carries a silent trap:
    `--set-section-alignment` must match the *pre-rename* name `.data`; spelled
    `.rodata` in the same invocation it is ignored, giving an object that links
    cleanly and fails at runtime on the alignment check.

    **What actually removes the pain is late binding, filed as 01a03b73-93a3.**
    Once the driver is resolved on `PATH` and any driver works -- `g++` and `c++`
    were both verified to assemble and link this correctly -- the assemble step
    costs a user nothing they do not already need. What an emitter would still
    buy is the quoted-path hazard and one subprocess, against writing and
    maintaining an ELF *and* a Mach-O writer and taking over the `-arch` and
    universal-binary handling the driver currently does for us.

    Reopen if: the link stops needing a driver, a Mach-O emitter arrives for
    another reason, or the quoted-path handling in `checkIncbinPath()` proves
    insufficient in practice rather than in theory.
