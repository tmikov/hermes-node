The build-native / --build-exe payload assembly (payloadAssembly() in
lib/build-exe/build_exe.cpp) emits the native-unit table
(hermesNodeNativeUnits) as a sequence of `.quad` directives -- 8 bytes
per entry, unconditionally, regardless of target. tools/hermes-node/
bundle_main.cpp declares the corresponding C symbol as
`void *const hermesNodeNativeUnits[]`, which only agrees with an
8-byte stride when sizeof(void *) == 8.

On a 32-bit target this would silently disagree: indexing
hermesNodeNativeUnits[1] would land in the middle of the first 8-byte
slot instead of at the start of the second, reading garbage bytes and
calling them as a function pointer via hermes_init_sh_unit. This is
exactly the silent-corruption failure mode the codebase otherwise
guards against (see hermesNodeNativeUnitCount, which is deliberately
uint64_t rather than size_t for the same reason).

A `static_assert(sizeof(void *) == 8, ...)` was added beside the
declaration in bundle_main.cpp (Task 13, native-compilation stack) to
turn this into a compile error rather than a silent garbage read. That
assert stops the damage but does not solve the underlying problem: a
real 32-bit port needs the emitter (payloadAssembly(), which would have
to emit a 4-byte stride, e.g. `.long`, on such a target) and the
consuming declaration to agree on element width, probably by deriving
both from a single shared constant rather than each independently
assuming 8.

This is currently inert: the project ships only 64-bit Linux and macOS
builds and has no cross-compilation story. Filed as a recorded
limitation, not an active defect, per an external review of Task 13.
