`--build-exe` cannot work on a released `hermes-node`, because no release
contains the kit it links against.

`.github/workflows/release.yml` stages the binary alone -- `cp
build/bin/hermes-node "staging/${NAME}/"` on both the Linux and macOS jobs --
and there is no `install()` rule for the kit in
`tools/hermes-node/CMakeLists.txt`. `resolveKitDir()` looks beside the running
binary, finds no `kit.manifest`, and the verb fails there.

So for anyone who did not build from source, the feature does not exist. That
is the reason the other build-exe issues matter: fixing the manifest's absolute
paths makes a kit portable between machines, but nobody outside this repo has a
kit at all.

CLAUDE.md records this as deliberate and unmade rather than overlooked: a
Release kit is ~40 MB against a binary of a few MB, so shipping one is a product
decision about download size. That decision is what this issue is for. Options,
roughly in increasing cost:

- Ship the kit as a **separate** release asset, so `--build-exe` users download
  it and nobody else pays.
- Ship it in the main tarball and accept the size.
- Leave it source-only and say so in the docs, which at least stops the feature
  from looking available when it is not.

Whatever is chosen, note the kit is invalidated by every commit: `kit.manifest`
pins the `git describe` version and the consumer compares it for exact string
equality. A release kit and its binary must therefore be cut from the same
build, which is an argument for doing it in the release workflow rather than by
hand.

- 2026-08-26T03:03:58.246Z  Tzvetan Mikov <tmikov@gmail.com>  comment
    Note from the portability work of 2026-08-26: shipping a kit and producing
    portable binaries are the same decision wearing two hats.

    A kit is archives cut from one machine's build, and `kit.manifest` records
    that machine's absolute library paths (01a03b73-781a). An executable linked
    against it inherits that machine's ICU soname and glibc symbol floor
    (01a03b73-c62a). So a released kit would let people run `--build-exe`, and
    what they got would be a binary that runs on machines resembling our CI
    runner -- not the "works anywhere" artifact the feature's name suggests.

    That does not block shipping a kit; it means whatever announces it has to be
    honest about the reach of what it produces. It also raises the value of
    01a03c05-2967, the glibc build baseline, since a released kit built in a
    manylinux-style container would produce artifacts with a far wider reach at
    no cost to the person using it.
- 2026-09-03T02:22:02.255Z  Tzvetan Mikov <tmikov@gmail.com>  comment
    Constraint discovered 2026-09-03 while revisiting 01a03b73-c62a: **whatever
    ships a kit must cut it in the same environment we want produced
    executables to run in.**

    A kit is not neutral about glibc. `__isoc23_strtoul` and `__isoc23_strtoull`
    are literal undefined symbol names *inside* `libhermes-node-kit.a`, baked in
    when the kit was compiled by glibc's `_GNU_SOURCE` header redirect -- unlike
    `fmod` and `arc4random`, whose version is chosen at the user's final link. A
    machine with glibc older than the one that cut the kit therefore cannot link
    against it at all: undefined symbol, at link time, before anything runs.

    `.github/workflows/release.yml` builds `build-linux` on `ubuntu-latest`,
    which is 24.04 and glibc 2.39. So shipping a kit from that job as it stands
    would not merely give users a high floor -- it would hand every executable
    any user ever produces our build machine's floor, permanently, and the
    failure they see would be a link error in someone else's toolchain rather
    than anything this project reports.

    This does not change what this issue asks for, and it is not a reason to
    delay it. It is a requirement on the implementation: sequence it with the
    baseline decision on 01a03c05-2967, and cut the kit wherever the binary is
    built.
- 2026-09-03T14:47:03.056Z  Tzvetan Mikov <tmikov@gmail.com>  status: open -> closed (fixed)
    Fixed for Linux. `.github/workflows/release.yml` builds the kit, smoke-tests
    it, and stages it at `kit/` beside the binary -- the path `resolveKitDir()`
    defaults to -- so `--build-exe` works from a release tarball with no `--kit`
    flag.

    **Option taken: the main tarball, not a separate asset.** This issue reserved
    that as a product decision, so the reasoning is recorded rather than assumed.
    The main tarball is the only layout in which the feature works untouched; a
    separate asset means the user must unpack it to exactly `<exe dir>/kit` or
    pass `--kit` every time, which is friction and a support burden for a flag
    that exists to be invisible. Measured cost, Release, linux-x64:

    | tarball | compressed | unpacked |
    |---|---|---|
    | binary only (as today) | 4.97 MB | 11.6 MB |
    | binary + kit | 16.3 MB | 51 MB |

    So the download roughly triples. If that is the wrong trade, flipping to a
    separate asset is a small change to the staging and upload steps and nothing
    else -- the kit contents and the smoke test stay as they are.

    **What the release job now does**, beyond staging:

    - Builds `hermes-node-kit` explicitly. `check-hermes-node` already DEPENDS on
      it, so this is a no-op on the tested path and the only source of a kit on
      the `skip_tests` one.
    - Smoke-tests it: bundles a one-line script, runs `--build-exe` against the
      staged kit, executes the result and checks its output. Shipping a kit that
      cannot link is worse than shipping none, because the failure lands in a
      user's toolchain rather than in our CI.
    - Copies the four kit files by name rather than the directory, so `kit.stamp`
      (a build-system artifact) does not ship and a renamed output fails loudly
      instead of silently producing an incomplete kit. The archives are not
      stripped; they are link inputs.

    The version-skew hazard this issue raised is handled by construction: the kit
    and the binary are cut from the same build in the same job, so the
    `git describe` string they compare cannot differ.

    **macOS still ships no kit**, and that is deliberate rather than pending.
    A macOS kit would be universal, and CLAUDE.md records that `ld -r`, `libtool`
    and `lipo` all emit a valid-looking *empty slice* for a missing architecture
    -- warnings only, exit 0, and `lipo -info` reports it as real -- which
    surfaces as an undefined `_main` at the user's link. A smoke test on the
    arm64 runner would not catch an empty x86_64 slice, so the check that makes
    Linux safe here does not transfer. Split to 01a067bc-78e5.
