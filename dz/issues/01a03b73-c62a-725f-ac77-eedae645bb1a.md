A `--build-exe` artifact is not portable off the machine that built it. The
point of a single-file executable is handing someone a file that runs; this one
runs on Ubuntu 24.04 and roughly nothing else.

Measured on `/usr/local/bin/dz`, which is itself a `--build-exe` artifact of
this tree:

    $ ldd /usr/local/bin/dz
        libicuuc.so.74, libicui18n.so.74, libicudata.so.74
        libstdc++.so.6, libgcc_s.so.1, libm.so.6, libc.so.6

    $ objdump -T ... | grep -o 'GLIBC_[0-9.]*'    -> up to GLIBC_2.38
    $ objdump -T ... | grep -o 'GLIBCXX_[0-9.]*'  -> up to GLIBCXX_3.4.31

So the floors are ICU **74**, glibc **2.38**, GLIBCXX **3.4.31**. Against them:
Debian 12 has glibc 2.36 and ICU 72; RHEL 9 has glibc 2.34; Alpine is musl and
has no chance. Each of those fails to start, with a dynamic-linker error rather
than anything this project controls.

The four components have genuinely different fixes and should probably become
separate work even though they are one symptom:

- **libstdc++ / libgcc**: `-static-libstdc++ -static-libgcc`. Cheap, no
  external cost.
- **ICU**: `HERMES_USE_STATIC_ICU=ON`, already named in CLAUDE.md, at the cost
  of a static system ICU at build time. Removes three of the seven libraries
  and the hardest version pin.
- **glibc floor**: not fixable by flags. Needs the release build to happen
  against an older baseline (a manylinux-style container, or the oldest Ubuntu
  we care to support). A CI change, not a code change.
- **musl / Alpine**: a separate build target, if we want it at all.

macOS is not affected the same way -- CLAUDE.md records that a produced macOS
binary needs only OS-provided libraries.

Note this is a property of how `hermes-node` itself is built, so it is inherited
by every produced executable; nothing in the `--build-exe` code path causes it.
