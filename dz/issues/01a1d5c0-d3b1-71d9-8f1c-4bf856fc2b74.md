If `createWindow` is rejected late -- in `onSharedContextReady`, after
Sokol's window already exists (the surface allocation, the window object
or the frame origin failing) -- the platform thread keeps running Sokol's
loop and keeps converting every real event into `gInput`
(tools/hermes-node-ui/ui_platform.cpp, `uiHandlePlatformEvent`). Nothing
drains it: event delivery opens only from the success path
(`openEventDelivery`), and since the Slice C fix wave there is no published
window either. So the queue grows for as long as the process lives --
every mouse move over a window the program can no longer use.

Narrow: the failure paths are the rare, mostly unrecoverable ones, and a
program that got the rejection usually exits. The fix belongs with Task
15's teardown, which owns what an abandoned window does (stop converting,
or tear the window down). Found by the Slice C whole-slice review.

    Task 15 (lifecycle and CLOSING) is done and did not take this on: its plan,
    Design (f) 3, declines it, so "the fix belongs with Task 15's teardown" no
    longer holds. There is no teardown to put it in: a windowed process never
    tears its window down, and ends in _exit() on the JS thread.
    
    What remains is the same defect in more states. The platform thread keeps
    converting every real event and pushing it onto gInput in three states where
    nothing on the JS thread will ever drain it:
    
    - after a late createWindow rejection (the original report);
    - in the limbo a program enters when it has replaced process.exit with a
      function that returns, and then closes the window: CLOSING has closed the
      dispatcher, so no dispatch is ever posted, and the process lives on;
    - while 'exit' listeners run, in every CLOSING.
    
    The third is bounded, because the listeners end and the process _exit()s.
    The first two are unbounded for as long as the process lives. In all three
    the platform thread never blocks on the queue, so the cost is memory, not a
    hang.
