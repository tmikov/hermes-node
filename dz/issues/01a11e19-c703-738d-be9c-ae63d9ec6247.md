`lib/process/node_process.cpp` (target `hermesNodeProcess`) calls `napi_*`
functions, but `lib/process/CMakeLists.txt` declares only
`target_link_libraries(hermesNodeProcess PUBLIC uv_a)`. Nothing tells CMake
that the library needs `hermesNapi`, so with static archives a consumer has
to put `hermesNodeProcess` before `hermesNapi` on its own link line by hand,
or the `napi_*` references stay undefined.

Two consumers already carry that workaround, in `unittests/CMakeLists.txt`:

- `CompileCacheRunTest` lists `hermesNodeCompileCacheRun`, then
  `hermesNodeProcess`, then `hermesNapi`, with a comment saying why: the Wasm
  hooks reach the bundle runner and, through it, `hermesNodeProcess`, which
  calls `napi_*`, so `hermesNapi` has to come after it on the line.
- `NodeProcessTest` lists `hermesNodeProcess`, `hermesNapi`, `hermesvm_a` in
  that order for the same reason.

Found during the native-wasm work (2026-10-08), when `CompileCacheRunTest`
started reaching `hermesNodeProcess` through the Wasm cache hooks. The
`hermes-node` binary does not hit it: it links `hermesNapi` whole-archive
(`--whole-archive` / `-force_load`, `tools/hermes-node/CMakeLists.txt`), so
every NAPI symbol is defined whatever the order. An ordinary consumer gets no
such help.

Fix direction: declare it -- `target_link_libraries(hermesNodeProcess PUBLIC
uv_a hermesNapi)` (PUBLIC or INTERFACE, since the references are in the
archive's own objects) -- and then drop the hand ordering and its comment from
the two unit tests. Check first that `hermesNapi` being force-loaded into
`hermes-node` (so `dlopen`ed addons resolve the NAPI surface; see
`tools/hermes-node/CMakeLists.txt`) is unaffected by it also arriving as an
ordinary transitive dependency, and that the kit's link line (cut from the
same CMake link by `utils/make-kit.py`) still keeps `libhermesNapi.a`
separate from the merged archive.
