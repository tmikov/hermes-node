Found while trying to get a ~1,500-module measurement for Task 16 of the
native-compilation plan, using examples/flow-bundler's real npm
dependencies (its own bundler entry cannot be used at all -- separate,
already-known issue, see progress-native-compilation.md).

`@babel/core/lib/config/files/import.cjs` is:

    module.exports = function import_(filepath) {
      return import(filepath);
    };

Dynamic `import()` inside a `.cjs` file is a Hermes parse error. The
bytecode path (`--build-bundle`) tolerates this: the file is not the
entry, so the scanner packages it as a module that throws if ever
required, and the build succeeds. `build-native` does not tolerate it:
any `shermes` failure on any discovered module is an unconditional hard
build error, by design (see CLAUDE.md's "Native Compilation" section,
"Failure policy"). The scanner discovers `import.cjs` by static scan of
`module-types.js`'s literal `require("./import.cjs")` regardless of
whether the running program's code path ever reaches it.

The practical consequence: since nearly every `@babel/core`-based plugin
transitively requires `@babel/core` itself (for `declare()` from
`@babel/helper-plugin-utils`, or directly, as `@babel/plugin-transform-classes`
and `@babel/plugin-transform-flow-strip-types` do), and `@babel/core`
always ships this same file, `build-native` cannot compile most
real-world programs that use Babel at all -- not just ones that call
`import()` themselves. Confirmed directly: `build-native` fails, unpatched,
on any entry requiring `@babel/core` transitively.

This is not a bug in the implementation of the fail-hard failure policy --
it is doing exactly what it was designed to do. It is a gap in how far
that policy reaches in practice, which was not obvious from the design
doc's own reasoning (which argued from the policy's correctness, not from
how many real graphs would hit it). Two directions worth considering,
neither decided here: teach build-native to tolerate a shermes failure on
a module the scanner also could not fully resolve statically the same way
the bytecode path does (recompile is impossible either way, but a
throwing native stub could exist if the unit table format allowed a
"stub" unit with no compiled code); or narrow the scanner's discovery so
files reachable only through a dynamic-`import()`-shaped indirection are
treated as unreachable-until-required, matching how a computed require()
is already handled.

For Task 16's own measurement, the one file was worked around locally
(outside git, in the gitignored node_modules) by replacing it with an
equivalent that throws synchronously instead of calling import().

Filed from Task 16 of the native-compilation plan.

    Fixed by Task 17. lib/bundle/bundle_build_native.cpp now classifies a
    shermes/cc CommandResult (Task 5's Exited/Signalled/SpawnFailed/WaitFailed
    split) instead of hard-failing every failure. A source rejection --
    Exited, non-zero, with diagnostics captured -- on a module that is
    neither the entry nor a preload is recompiled as a native throwing stub
    (reusing bundle_build.cpp's makeThrowingStub, moved to external linkage
    so both producers share one implementation), under the bytecode
    producer's own "cannot compile" warning wording, and counted in
    stubbedModules. Anything that is not a source rejection (a crash, a spawn
    or wait failure, a nonzero exit with no diagnostic text, or a zero exit
    that wrote nothing) still hard-fails, exactly as before, so a toolchain
    defect cannot be mistaken for a throwing stub.

    Correction to this issue's own description: return import(filepath) (the
    actual @babel/core shape, called from inside a function) is not a Hermes
    PARSE error -- it parses fine and is rejected only in IRGen, which the
    shared scanner never reaches. The bare-statement form measured in the
    original design doc was a parse error; the two forms differ, and only the
    first is what @babel/core ships. See the corrected "Failure policy"
    section in docs/superpowers/specs/2026-09-13-native-compilation-design.md
    and in CLAUDE.md.

    Verified: the exact repro in this issue (an entry requiring a .cjs with
    return import(f)) now builds successfully under build-native with the
    expected warning, and the produced executable runs and throws when the
    bad module is required, matching --build-bundle's behavior exactly.
    test/build-native-tolerant.js pins both the tolerant case and a hard
    failure case (--cc=%false) that must not be swallowed.
