`test/build-native-builtins.js` asserts a default `build-native` artifact
carries exactly one Hermes bytecode blob per architecture slice (Hermes's own
`ExtensionsBytecode`). `test/fixtures/native/count-magic.py` counts that by
searching the whole file for the 8-byte bytecode magic
`0x1F1903C103BC1FC6`. On x86-64 that pattern also occurs in machine code:
a function that compares against or writes the magic loads it with
`movabs $0x1f1903c103bc1fc6,%reg`, which embeds all eight bytes contiguously.

Measured on Linux x86-64, ASAN Debug build, at `ea20949`: the native artifact
reports `slice 0 has 6, expected 1..1`. Mapping each hit back with objdump and
addr2line:

- `hermes::hbc::SimpleBytecodeBuilder::generateBytecodeBuffer()` -- movabs
- `hermes::hbc::(anon)::sanityCheck(...)` -- movabs
- `hermes::node_compat::(anon)::bundleLoadCallback(...)` -- movabs (our code)
- `hermes::hbc::BCProviderFromBuffer::isBytecodeStream(...)` -- in .text
- `hermes::hbc::(anon)::BytecodeSerializer::serialize(...)` -- in .text
- one hit in data, the genuine blob

Only the last is bytecode. On arm64 a 64-bit constant is materialized with
movz/movk, so the eight bytes never appear together in code; the test was
written and measured on macOS arm64, which is why it passed there. It has
never been able to pass on x86-64 Linux -- it is not a regression from the
Hermes submodule update it surfaced under: `bundle_run.cpp` is unchanged by
that update and alone contributes a code hit.

The `--bytecode-builtins` half (`180 9999`) is unaffected in practice, since
a lower bound tolerates extra hits, but it is inflated by the same five.

Fix direction: for ELF, count only in non-executable sections (skip
SHF_EXECINSTR) -- or more simply, in the sections that can hold the blobs.
Mach-O needs no change, though applying the same rule there (skip
`__TEXT,__text`) would keep the two paths symmetrical. Counting only 8-byte-
aligned offsets is not a fix: a code immediate lands aligned one time in
eight.
