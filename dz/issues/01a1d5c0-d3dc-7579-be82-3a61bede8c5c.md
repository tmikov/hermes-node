Sokol's X11 loop takes `count = XPending(display)` and then calls
`XNextEvent` `count` times (sokol_app.h, `_sapp_linux_run`). Our clipboard
read (tools/hermes-node-ui/x11_clipboard.cpp) runs inside that batch -- a
Ctrl+V's paste read is made from `event_cb` -- and removes events from the
same queue with `XCheckIfEvent` (the owner's SelectionNotify, the scratch
PropertyNotify). If an event that was counted is one our read then takes,
the batch's remaining `XNextEvent` calls outnumber the queued events, and
the last one blocks until the next X event arrives -- a frame that is not
presented until the user moves the mouse.

Narrow: it needs a reply (or a stale notify) that was already queued when
Sokol counted, and a quiet server afterwards. Recorded by Task 12's
re-review; not reproduced. A fix is to let Sokol's batch see only events
that are still there, or to do our read outside the batch.
