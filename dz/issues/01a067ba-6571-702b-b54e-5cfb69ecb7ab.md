`hermesNapi` calls `dlopen`, `dlsym`, `dlerror` and `dlclose` in
`hermes_napi_load_module()` but does not link the dl library, so every
consumer has to supply it and nothing says so.

glibc merged libdl into libc at 2.34, which is why this has never been
noticed: on any host that new the calls resolve with no `-ldl` anywhere and
the missing dependency is invisible. Against glibc 2.28 it is undefined
references at the link of everything that pulls hermesNapi in.

Found 2026-09-03 building in `almalinux:8` for 01a03c05-2967. It broke, in
order:

- every unit test that links `hermesNapi` (`BindingRegistryTest`,
  `CompileCacheRunTest`, `ModuleLoaderTest`, ...)
- Hermes's own `bin/hermes` CLI, `hermes/tools/hermes`, which the lit suite
  needs for the primordials test

Not `hermes-node` itself, which picks up `-ldl` by another route -- which is
exactly why the first container build looked like a clean pass. It is only
the *tests* and the *other* tool that fail, so a build-only check does not
catch this.

**Worked around in this repo, not fixed.** `CMakeLists.txt` attaches
`${CMAKE_DL_LIBS}` to the `hermesNapi` target right after
`add_subdirectory(hermes)`, on the producing target so a consumer added later
cannot forget it. The plain `target_link_libraries` signature is required
there: `Hermes.cmake:141` already links that target plainly and CMake refuses
to mix the two forms.

**The real fix is one line in `hermes/API/napi/CMakeLists.txt`**, in the
submodule, on the `hermes-node` branch of `github.com/tmikov/hermes`. Doing
it here would leave the submodule dirty, so it was not done. When it lands
upstream, delete the block in our `CMakeLists.txt` -- it is commented with a
pointer to this issue's reasoning.

Note the workaround only covers targets in *our* build. Anything inside the
Hermes tree that links `hermesNapi` in a standalone Hermes build is still
broken on pre-2.34 glibc.
