CI builds macOS with `HERMES_NODE_ENABLE_UI=ON` in the `asan-debug-o1`
configuration, and that job now compiles the Metal backend. Nobody knows
whether GitHub's macOS runners have a Metal device or a window-server
session with a usable display.

The job is green either way. Every window test is gated on the `display`
lit feature, which on macOS is decided by running the binary on
`test/fixtures/hnui-demo/display_probe.js` and requiring a drawable; with
no display those tests report UNSUPPORTED. `display-expected` is false on
macOS CI, so the canary `test/ui-display-feature.js` is UNSUPPORTED there
as well. The cost of not knowing is that the Metal window tests may be
running nowhere but on one developer machine, with nothing saying so.

`.github/workflows/ci.yml` has a step, "UI display probe (informational)",
that runs the probe by hand with tracing on and prints the console-session
verdict and the probe's exit status. It cannot fail the job. The comment
above it lists the three outcomes.

To close this: read that step's output in the first pull-request run after
it landed.

- A display (`present: drawable acquired` and `DISPLAY_PROBE_OK`): set
  `HERMES_NODE_UI_EXPECT_DISPLAY: 1` for the macOS job, so the canary
  guards it from then on, and close this.
- No Metal device, or a device and no drawable: record which here, and
  leave the workflow as it is. The Metal window tests are then local-only,
  and that is what this issue stays open to say.
