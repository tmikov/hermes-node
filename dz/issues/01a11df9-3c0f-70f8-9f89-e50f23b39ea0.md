`build-native -O0` (and `-O1`, `-O2`, `-Os`) does not reach `cc` when the
kit was cut from a Release build. `buildCompileCommand()`
(`lib/build-native/native_compile.cpp`) pushes the per-build flag from
`ccOptFlag(opt)` at line 164, then forwards the kit manifest's whole
`driverflag` list after it (lines 173-174). A Release kit records
`driverflag: -O3` (`cmake-build-release/kit/kit.manifest`, line 17), and the
last `-O` on a driver command line wins, so every JavaScript and Wasm unit is
compiled at `-O3` whatever the user asked for. An ASAN/Debug kit records
`-g` and no `-O`, so the flag does work there -- which makes the behaviour
depend on which configuration the kit was cut from.

Measured on hermes-parser's WebAssembly module (768,303 bytes of Wasm,
32,697,631 bytes of generated C), Release kit, x86_64 Xeon E-2288G, 16
cores, 2026-10-08, `/usr/bin/time -v` on the `cc` step:

| compile | wall | peak RSS | object |
| --- | --- | --- | --- |
| `build-native -O0` as built today | 176 s | 1,448,580 KiB (1.38 GiB) | 25,068,984 bytes |
| `build-native -O3` | 176 s | 1,448,044 KiB (1.38 GiB) | 25,068,984 bytes |
| true `-O0` (manifest `-O3` removed by hand) | 18 s | 1,170,200 KiB (1.12 GiB) | 25,606,184 bytes |

The first two rows are the same compile: the objects are the same size to
the byte. A real `-O0` is about ten times faster on this file. Details in
`docs/superpowers/plans/progress-native-wasm.md` (Task 1).

This probably also explains a figure CLAUDE.md records under "Native
Compilation" -- `-O0` measured only about 10% faster than `-O3` on tetris,
against a predicted 4x -- if that kit recorded `-O3` too. Not re-measured.

Fix direction: emit the per-build `-O` flag after the driver-flag list (the
target-selecting flags are not order-sensitive against `-O`), or filter `-O*`
out of `driverFlags` when building a compile command. Either way a
`BuildNativeTest` case should assert that the last `-O` on the argv is the
requested one, for a manifest that carries its own.
