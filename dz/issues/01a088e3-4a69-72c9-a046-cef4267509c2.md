`hermes_run_bytecode`'s documented contract (`hermes/API/napi/hermes_napi.h`)
says it returns `napi_pending_exception` on a JS error and
`napi_generic_failure` on a bytecode validation failure. The implementation
does not: a buffer `createBCProviderFromBuffer` rejects is reported by raising
a SyntaxError and returning `napi_pending_exception`, the same status and the
same observable shape as a module whose own top level threw
(`hermes/API/napi/hermes_napi.cpp:751-754`).

So a caller cannot tell the two apart, and they need opposite handling. A
module that throws on load is the program's business and must propagate
through `require()`. Bytecode this runtime will not load is a damaged
artifact and must terminate -- see `fatalBadPayload()` in
`lib/bundle/bundle_run.cpp`.

Worked around there by checking `hbc::MAGIC` before calling, which is the
first thing `BCProviderFromBuffer::isBytecodeStream()` checks. That catches
damage to the start of a payload and nothing subtler: a payload whose magic
survives but whose interior is broken still reaches `hermes_run_bytecode` and
still throws, so a damaged container of that shape stays catchable by an
optional-dependency probe. The workaround also costs the run layer the llvh
include paths for two constants.

The fix is one line in Hermes -- return `napi_generic_failure` for the
provider-construction failure, as the header already promises -- after which
the magic check and its include paths come out and the check becomes exact.
Needs the hermes submodule, whose branch state is mid-flight, so it is
recorded here rather than done.
