Every ImGui addon test was shown able to fail by a mutation, and each
mutation is recorded in `docs/superpowers/plans/progress-imgui-addon.md`
(Mutations). Some behaviours of the addon survived their mutation, or
are reached by no test at all. They are listed here so that a later
change does not assume a test guards them.

Survived a mutation (the suite stayed green):

- **Previous image and view not destroyed on a texture replace**
  (Task 6, mutation (c)). `updateTexture()` in
  `addons/imgui/imgui_renderer.cpp` destroys the old pair only once the
  new one is valid. Leaking it exhausts Sokol's pools only after thousands
  of replacements, which no test performs. A test would replace the atlas
  in a loop (the `glyphs` scene at a new size each frame) past Sokol's
  image pool size and require no `[sokol-` line; or the addon could expose
  Sokol's live image count through `__test.state()`.
- **Repeated key-down dropped** (Task 7, (b)). Passing a `repeat` key-down
  on is harmless at this ImGui version, because `AddKeyEvent` filters a
  down for a key already down. The drop is kept as the design states.
- **`key != ImGuiKey_None` guard** (Task 7, (f)). `AddKeyAnalogEvent`
  returns at once for `ImGuiKey_None`, so removing the guard changes
  nothing visible.
- **`AddFocusEvent(true)` on `HNUI_EVENT_FOCUS`** (Task 7, (g)). Regaining
  focus only clears ImGui's `AppFocusLost`, which no case reads. A test
  would blur, then focus, then require a held key to register again (ImGui
  clears key state on focus loss).
- **`HNUI_EVENT_PASTE` handled as well as the chord**: tracked separately
  in 01a21c37-6c02.
- **Modifier events skipped** (Task 7, (e)) is not caught by
  `ui-imgui-input.js` but is caught by `ui-imgui-clipboard.js` (Task 8,
  (c)); listed only so nobody repeats the check.

Reached by no test:

- **The white-fallback view.** A command whose texture id is
  `ImTextureID_Invalid` samples the 1x1 white image. ImGui hands no such
  command to the renderer in any scene. (Mutation (b) of Task 6, every
  command bound to white, is caught; the fallback itself is not.)
- **The failed-upload paths**: `texture <id> failed (format <f>)` for a
  non-RGBA32 texture, `texture <id> failed` for an invalid image or view,
  and the draw loop's skip of a command whose texture has no id.
- **`device objects failed`, `pipeline failed`, `buffer could not grow`**
  and the `sokol backend lacks draw_base_vertex` refusal: every one needs
  Sokol to refuse a resource or a feature it grants in every build here.
- **`event rejected: size <n>`**, the listener's refusal of an event
  smaller than `HNUI_EVENT_MIN_SIZE`: a host built from this tree never
  sends one.
- **The `quad` scene's error paths**: first use outside a frame callback,
  and a failed image creation, both of which throw.

A test for the failure paths would need a way to make Sokol refuse,
for example a test-only hook that exhausts a pool before the first draw.
Whether that is worth having is undecided.

    Three more, from the final whole-branch review (2026-11-27):

    - **The pipeline rebuild when a target's colour format or sample count
      changes** (`ensurePipeline()`'s destroy-and-remake path in
      `addons/imgui/imgui_renderer.cpp`) is reached by no test. Every target
      the host hands out here has the same format and sample count, so the
      pipeline is made once and only the early return is ever taken after
      that.
    - **`texture <id> failed` printed once per texture.** A failed upload
      keeps ImGui's status and is retried at every `render()`;
      `gFailedTextures` keeps its trace to one line per texture until an upload
      succeeds or the texture is destroyed. No test reaches it, for the same
      reason as the failed-upload paths above: Sokol never refuses the image
      here.
    - **`Renderer_TextureMaxWidth`/`Height` clamped to the device's
      `max_image_size_2d`** in `rendererInit()`. The clamp only acts when the
      device limit is below 8192; the GL driver the suite runs on reports
      16384 (read with a temporary trace), so no test can see it act.
- 2026-11-27T10:14:40.237Z  Tzvetan Mikov <tmikov@gmail.com>  comment
    From the Codex review of the addon (2026-11-27):

    - **Corrections to the comment above.** `gFailedTextures`' entry is
      cleared when an upload succeeds or when the renderer destroys the
      texture (the `WantDestroy` branch of `updateTexture()`). A texture
      ImGui discards itself, which it does for one that has no texture id and
      no `BackendUserData` (`imgui_draw.cpp`, the `WantDestroy` to `Destroyed`
      shortcut), never reaches the renderer and keeps its entry. Nothing can
      observe that, since ImGui never reuses a texture id.
    - **A view is now made only of a valid image**, in `updateTexture()`, the
      white fallback and the `quad` scene. Before, `sg_make_view()` ran on
      whatever `sg_make_image()` returned, and with Sokol's validation layer a
      view of an invalid image is a validation error followed by an assertion
      that aborts the process, so the "previous texture kept, upload retried"
      path could not survive its own failure.
    - **The failed-upload path is still reached by no committed test**, but a
      test for it was written and run: a test-only scene that makes 1x1
      images until `sg_make_image()` answers an invalid id (the producing
      instance keeps Sokol's default image pool of 128; 123 were free), drawn
      in the frame that makes ImGui update the font atlas. With the fix it
      showed `texture 1 failed` once across seven frames, the previous atlas
      texture kept and still drawing, and `replaced` once the images were
      freed; with the old order the process aborted (exit 134). What blocks
      it is the stderr rule: Sokol logs every refused `sg_make_image()` as
      `[sokol-produce:error] item 154: IMAGE_POOL_EXHAUSTED: image pool
      exhausted` (the item number only, no text, in a build without
      SOKOL_DEBUG), which every window test must exclude. Landing the test
      needs that rule narrowed for it in `utils/check-ui-stderr-rule.py`, as
      it is for two tests already, with the test itself then requiring that
      every `[sokol-` line is that item. Whether to narrow it is undecided.
